## 一、适用对象与业务假设

服务对象是**外贸采购代理**：替海外客户在国内找货、下单、验货、发运，赚取差价与服务费。
所有功能取舍都以这条业务链为准，而不是以"通用 ERP 该有什么"为准。

写任何一个模块之前，先确认它是否服务于下面这 6 条假设。违反假设的功能先不做。

| # | 假设 | 对设计的直接影响 |
|---|---|---|
| 1 | 客户在境外，主币种是 USD / EUR，本币 CNY 记账 | 币种与汇率不是"以后再说"的字段，而是**底座**：金额、成本、毛利都得分币种与本币两套账 |
| 2 | 一笔生意是"客户下单 → 我方采购 → 验收 → 报关出口 → 收汇" | 单证的链条是单向的，但要能**反向追溯**：从一笔收款查到它核销了哪几票出货 |
| 3 | 常常"以销定采"，先有订单再找供应商 | 采购订单必须能挂到销售订单行上，否则算不出单票毛利 |
| 4 | 多数时候不持有库存（工厂直发），但会备货、会合并出货 | 库存不能设计成"必须有入库才能出库"；出货与订单是多对多 |
| 5 | 一个主体可能既是客户又是供应商（客供两用） | 已在 `md_partner` 用角色位掩码解决，新模块一律引用 partner，不再建客户表 |
| 6 | 报关资料、发票抬头、付款主体常常不是同一个人 | 主体类型（公司/个人）与结算条件要独立成字段，不能塞进备注 |

## 二、业务主链

所有模块都挂在这条链上。链断在哪一环，那一环就是下一个要做的模块。

```
询盘 ──▶ 线索 ──▶ 客户 + 联系人
                        │
                        ▼
                    报价单 ──▶ 销售订单 ──▶ 采购订单 ──▶ 产品货源
                                    │                       │
                                    ▼                       ▼
                                出货批次 ◀──────────── 收货 / 验货 / 库存
                                    │
                        ┌───────────┴───────────┐
                        ▼                       ▼
                    报关与物流                应收 / 应付
                        │                       │
                        ▼                       ▼
                    发运与单证              收付款核销 ──▶ 汇兑损益 ──▶ 单票毛利
```

链上有两处**跨域交叉**，是本项目"集成在数据层"的具体体现：

- 「客户 + 联系人」同时是 CRM 的跟进对象与 ERP 的交易对手——同一行 `md_partner`，不建第二张表。
- 「产品货源」把产品、供应商、采购价绑在一起，报价时的成本、采购时的单价都从它取；它被两侧引用，所以留在 `md_`。

## 三、优先级判定标准

| 级别 | 判据 | 处理方式 |
|---|---|---|
| **P0 阻断** | 缺了它，一笔生意跑不完（开不出单、收不到钱、算不清成本） | 必须先做，且不能只做半截 |
| **P1 支撑** | 单据能开，但人得靠 Excel 和记忆补（对账、跟进、追溯） | 完成 P0 后立刻补，否则系统会被绕过 |
| **P2 精细化** | 规模上来、毛利变薄之后才值得投入的度量与优化 | 明确排期，但不阻塞前两级 |

一条容易走偏的判断：**"能录进去"不等于 P0。** 一个字段只要不影响单据流转与钱的计算，
就是 P1 或 P2——先把链条接通，再回头补字段。

## 四、能力地图

### A. 共用底座

**业务目标**：让后面每个模块都不用各自处理"钱是什么币种、单据号怎么发、状态怎么流转"。
底座不做完就开单据，代价是所有单据表各带一套币种字段、各写一套编号逻辑，事后统一要改全部表。

| 编号 | 能力 | 要点 | 优先级 | 现状 |
|---|---|---|---|---|
| A1 | 多币种 `Currency` | ISO 4217 代码、小数位、**唯一本币**；停用不删除 | P0 | 已实现 |
| A2 | 汇率 `ExchangeRate` | 按币种 + 生效日存历史，带来源；只能追加不能覆盖历史；跨币种折算统一走一个函数 | P0 | 已实现 |
| A3 | 单据状态 `DocumentStatus` | 与 `EnableStatus` 严格分开的一套枚举；只允许状态机里的跳转 | P0 | 已实现 |
| A4 | 单号生成 | 案号派生（报价 / 订单）+ 类型月份流水（采购 / 送货单），唯一索引兜底，不靠"查最大号 +1" | P0 | 已实现（`{类型}-{YYYYMM}-{流水}`）；案号派生与 `{YYMM}-{NNN}` 待 T-47 |
| A5 | 往来单位商务条件 | 结算方式、账期天数、信用额度、默认贸易术语、默认币种 | P1 | 已实现 |
| A6 | 金额定点化 | 现有金额是 `float64` + `decimal` 列，累计误差会放大；阶段 5.5 的前置项之一 | P1 | 已知隐患 |
| A7 | 产品编号检索 `ProductCode` | 一个产品可挂多条编号（旧 SKU、客户图号、工厂型号），只服务搜索；关键词同时匹配 SKU 编码、中英文品名与全部编号 | P1 | 未实现（T-48） |

**为什么 A1/A2 排在所有单据之前**：报价单要报外币价、订单要折本币算成本、收款要记汇兑损益。
这三处如果各留一个 `currency string` 字段，后面统一口径要改全部表加全部历史数据。

**为什么 A4 不用"查最大号 +1"**：两个并发请求会拿到同一个号，而单号上有唯一索引，
失败的那一方报 500 而不是重试——这种错误只在并发下单时出现，测试很难覆盖。

**为什么 A7 单开一张表**：编号条数由客户与工厂决定，设计时定不了；在产品表上加 `code2` / `code3`
的那一刻，第四条就无处安放。也**不用 JSON 列**存数组——PostgreSQL 走 `jsonb`、MySQL 走 `JSON`、
SQLite 走 `json1`，三套语法，"换存储不改代码"当场作废。同样**不复用** `md_product_source.supplier_sku`：
那是"某供应商目录里的货号"，一个产品对 N 个供应商就有 N 条，删一条货源会连带把编号删掉。

**为什么 A7 的搜索用 `EXISTS` 不用 JOIN**：一个产品命中自己的多条编号时，JOIN 会让它在结果里
出现多行，分页与 `total` 一起错位；`count` 与 `list` 必须共用同一组条件。编号也**不上单据**——
一张单同时出现 SKU 与编号两套叫法，对账与客服口头沟通都会分叉；编号只回答"这个词能不能
找到这个产品"，身份永远由 `SKUCode` 回答。

### B. 客户与线索（CRM 域，`crm_` 前缀）

**业务目标**：把"询盘 → 成交 → 复购"的关系沉淀成可查询的资产，而不是散在个人邮箱与聊天记录里。
外贸的现实是**对接人会换、公司不会换**：换一个人接手，历史跟进不能跟着丢。

| 编号 | 能力 | 要点 | 优先级 | 现状 |
|---|---|---|---|---|
| B1 | 联系人 `Contact` | 一个主体多行；职位、语言、偏好渠道；可标记主联系人（时区未做） | P0 | 已实现 |
| B2 | 跟进记录 `Activity` | 类型（电话/邮件/拜访/报价/其他）+ 内容 + 下次跟进日期；挂在主体或联系人上（挂商机未做） | P0 | 已实现，挂商机待补 |
| B3 | 商机 `Opportunity` | 阶段枚举 + 状态机；金额、币种、赢单概率**分列存**，不用阶段反推 | P1 | 已实现 |
| B4 | 线索 `Lead` | 未建档主体的询盘；来源渠道与国别；转化时建 partner 并回填来源 | P1 | 已实现 |
| B5 | 客户分级 | ABC 等级、行业、付款习惯；**只做标签与筛选，不做权限** | P2 | 未实现 |

**B1 与 `md_partner.contact` 的关系**：那个列是**主联系人姓名**，退化为"快速看一眼"的冗余字段。
真正的联系人是多行、各有电话邮箱的 `Contact`。不要往 `md_partner` 上继续加 `phone2` / `email2`。

**B2 最容易做错的地方**：想给主体加一个"最近跟进时间"字段。那是派生数据，
应该由 `Activity` 聚合（或加缓存）。写进 `md_partner` 后，每处写主体的代码都要记得更新它，
漏一处的表现是"明明跟过客户，列表里显示三个月没联系"。

**为什么 B3 的概率要独立成字段**：阶段赢率是团队的经验值，具体商机的概率是业务员的判断。
用阶段反推，等于强迫所有人对同一个阶段给出同一个概率，销售预测立刻失真。

### C. 报价与订单（ERP 域，`biz_` 前缀）

**业务目标**：把"一口价"变成可追溯、可复用、能算清毛利的过程。
报价是这个行业最容易亏钱的地方：运费、汇率、退税三项任何一项估错，毛利就翻负。

| 编号 | 能力 | 要点 | 优先级 | 现状 |
|---|---|---|---|---|
| C1 | 产品货源 `ProductSource` | 一个产品对多个供应商；供应商货号、采购价、MOQ、交期 | P0 | 已实现 |
| C2 | 报价单 `Quotation` | 多轮版本、贸易术语、币种、有效期、试算成本与毛利率 | P0 | 已实现（阶梯价未做） |
| C3 | 销售订单 `SalesOrder` | 主表 + 明细行；金额由 service 汇总，不接受前端提交总额；状态机流转 | P0 | 已实现 |
| C4 | 采购订单 `PurchaseOrder` | 同上，**可挂销售订单**（以销定采），一张销售订单下可有多张采购单，也允许不挂单的备货采购 | P0 | 已实现（明细可挂销售订单行，表头不强制）；编号走独立号段 `PO-{YYMM}-{NNN}`，待 T-47 |
| C5 | 报价转订单 | 一次点击带出明细与价格，不重录；转换后报价单锁定 | P1 | 已实现 |
| C6 | 订单变更留痕 | 改价、改量记一条变更记录，谁改的、改前改后 | P2 | 未实现 |

**C1 为什么是 P0**：报价单上的成本来自"这个产品最近从哪家进的、什么价"。
产品表上的 `supplier_id` 只是**默认货源**，一个产品对多个供应商是常态（比价、备选、旺季分单）。
没有货源表，报价成本只能手填，手填的成本价就是毛利失真的源头。

**C1 落地时的三条口径**：① 查重维度是「产品 + 供应商 + 货号」，不是全局货号——
我方一个 SKU 拆成散装与彩盒两套编码、都从同一家同一个货号进货是真实做法；
② 采购价同样走四件套，缺当日汇率时返回 400 而不是把 0 写进本币价，
否则"最便宜的那家"会变成价格缺失的那家；③ 产品下还挂着货源时不允许删产品，
软删除不会带走子表，留下的行会在按供应商查货源时冒出来却点不进去。

**C2 的毛利率必须由后端算**：前端算毛利，等于把成本口径交给浏览器。
而且报价单要能锁定当时的成本快照——供应商涨价后回看三个月前的报价，应当仍显示当时的毛利。

**C2 落地时的四条口径**：
① 成本取该产品**本币价最低的启用货源**并锁进明细（也可指定货源）；
产品没有货源时直接拒绝报价——手填成本就是毛利失真的源头，而"没有货源"是一句能当场修好的提示。
② 报价币种可以与本币不同：单据锁一个汇率，明细落「原币金额 + 本币金额」，
毛利统一在本币口径算（成本本来就在本币侧），否则不同币种的额与成本没法相减。
③ 同一份报价共用 `DocNo`、只递增 `version`；**只有草稿可改可删**，已确认的只能另存新版本。
否则"发给客户的那一版"会被悄悄改掉。**升版本与新开一份报价是两条互斥的路**：
交易条件或明细集合变了（价格、数量、贸易术语、付款方式、有效期）→ 同一份报价升 `version`，`DocNo` 不动；
客户重新询价、或上一版已经转单 / 已失效 → 新开一份报价（`QT02`），拿新的 `DocNo`。
判据的实质是"这还是不是同一个承诺"：改的是同一笔生意的条件就升版本，谈的是另一笔就新开。
④ 报价单只用 `DocumentStatus` 里的「已确认 / 已取消」两个状态，其余阶段属于订单；
过期后既不能确认也不能转订单（`Quotation.ConvertBlocker`，T-13 直接复用）。

**C3 / C4 的三条硬规则**：

- 金额汇总只在 service 做。前端提交 `total_amount` 一律忽略，否则"改一行明细不改总额"是必然发生的。
- 状态只能按状态机跳转（草稿 → 已确认 → 备货中 → 已出货 → 已完成 / 已取消）。
  允许任意跳转等于没有状态，取消已出货的订单和取消草稿订单是两件事。
- 采购单**可以**不挂销售订单（备货），但要能挂。明细行的 `sales_order_item_id` 回答"这批货是为哪张单备的"；
  强制表头挂单只会逼人先造一张假订单，代价是备货采购的成本要等订单出现才归集得到单票毛利（T-22）。

**C3 落地时的三条口径**：① 入参 DTO 里**没有**合计字段，前端传 `amount_total` 在绑定阶段就被丢弃——
比"接收了再判空"更彻底，因为没有任何代码路径能读到它；② 订单不存成本与毛利，
那属于采购价（T-12）与运杂费，在订单上手填成本等于给毛利留第二个来源；
③ 只有草稿可改可删，已确认的订单是承诺，调整走变更单（T-24）而不是悄悄改原单。

**C4 落地时的三条口径**：① 「以销定采」落在明细的 `sales_order_item_id` 上，
校验三件事——行存在、产品一致、所属销售单未被取消；**不校验累计采购量是否超卖**，
分批向两家工厂下单是常态，卡在采购单上只会逼人拆单造假，用量对账属于 T-22；
② 采购币种与销售币种往往不同（收美元、付人民币），所以采购单单独锁一份汇率，
不复用销售单上那个；③ 采购价是谈出来的，不从货源表读价——`source_id` 只作追溯。

**C5 落地时的三条口径**：① 转出来的是**订单草稿**：客户确认的是报价，
订单要不要确认由业务决定，自动确认会让「已确认」这个状态失去意义；
② 币种、汇率、单价、数量全部沿用报价单，只允许补下单日与交期——
任何一项可覆盖，"转单时顺手改价"就没人发现得了；③ 幂等靠条件更新
（`WHERE sales_order_id IS NULL`）而不是先查后写：两个人同时点转单时只会有一个成功，
输的那一方把刚建的订单删掉并报 409，不留没人认领的草稿单。
已转单的报价单不可再改、不可作废（要停就停订单），也不可再转。

### D. 供应链与库存（ERP 域，`inv_` 前缀）

**业务目标**：知道货在哪、还能卖多少、什么时候能发。
采购代理多数时候直发，但"直发"也要有节点：工厂什么时候备好、验货过没过、哪天装的柜。

| 编号 | 能力 | 要点 | 优先级 | 现状 |
|---|---|---|---|---|
| D1 | 库存流水 `StockMovement` | 每次出入库一条记录，是库存的**权威来源**；带单据类型与来源单号 | P1 | 已实现（T-15）：手工录期初 / 盘盈亏 / 其它，单据类流水由 T-16 写入 |
| D2 | 库存快照 `StockSnapshot` | 当前库存，可由流水重算，用于对账与性能 | P1 | 已实现（T-15）：增量原子维护 + 全量重算对账，无写接口 |
| D3 | 出入库单据 | 采购入库、销售出库、调拨、盘点；盘亏盘盈走流水不直接改快照 | P1 | 已实现（T-16）：采购入库 / 销售出库 / 盘点；调拨待仓库维度（T-16b） |
| D4 | 出货批次 `Shipment` | 与**同一客户的**订单多对多（分批 / 合并）；必须有分配表记录"这一票出了哪几行的多少" | P0 | 已实现（T-14）：分配行 + 可出行查询 + 合并出货；尚未联动库存（T-40）；编号走独立的 `DN-{YYMM}-{NNN}` 套号，不带案号（§五.4.3） |
| D5 | 可承诺量 ATP | 现有库存 − 已分配 + 在途，用于接单前判断能否按期发 | P2 | 未实现 |

**D4 排在 D1 之前**：出货是订单链条的必经环节（不发出货就没有应收、没有报关）；
而库存流水只有在"我方持货"的场景才被用到，直发业务根本不产生出入库。

**D4 为什么必须有分配表**：一张订单分三次发、三张订单合并一个柜，是外贸的日常。
把订单号编进出货单号，或者让出货单只存一个 `order_id`，这两种做法都会在第一次分批出货时崩掉。

**D1 与 D2 的分工**：流水是事实，快照是缓存。**只允许由流水推快照**，不允许业务代码直接改快照，
否则"快照和流水对不上"这件事将无法判断是谁的错。

### E. 报关与物流（ERP 域）

**业务目标**：一票货从工厂到客户手上，单证齐、节点可见、费用进得了成本。
这一块的输入几乎全来自外部（海关、货代、船公司），所以**允许人工录入与附件**比自动化更重要。

| 编号 | 能力 | 要点 | 优先级 | 现状 |
|---|---|---|---|---|
| E1 | 商品报关要素 | 产品的 HS 编码、申报品名（中英）、材质用途、原产地、法定单位 | P1 | 已实现：产品侧六项默认值，全部选填；出货批次上的申报要素随 E4 落地 |
| E2 | 货代与承运人 | `Partner` 增加第三种角色位（货代 / 报关行），不新建表 | P1 | 已实现：`PartnerRoleForwarder`（位 `4`）+ `/forwarders` 入口 |
| E3 | 运费与杂费 | 海运费、报关费、拖车费、保险；可归集到出货批次，进单票成本 | P1 | 已实现：`biz_shipment_charge`，五类费用按原币 + 当日汇率折本币归集到出货批次 |
| E4 | 报关单 `CustomsDeclaration` | 报关单号、申报日期、监管方式、退单状态 | P2 | 已实现：`biz_customs_declaration`，一票多张（分票申报 / 退单重报）；不做状态机，顺序由操作的人负责 |
| E5 | 物流节点 | 提单号、船名航次、ETD / ETA、节点时间线 | P2 | 已实现：`biz_shipment` 四列 + 独立的 `PUT /shipments/:id/logistics`（任何状态可改，船期订舱后才有） |

**E2 复用 `Partner` 而不是新建表**：这是 `md_partner` 用位掩码的直接收益。
落地时确实只加了一个 `PartnerRoleForwarder = 4` 常量与一行展示名，判断逻辑一行没改：
按角色过滤靠 `RoleValuesContaining` 展开成 `IN`，加一位自动覆盖。
反过来说，如果当初用了 `1/2/3` 的连续枚举，这里就得改所有分支并把 3 插到 7。

**E1 为什么不做成产品的必填字段**：HS 编码随目的国与用途变，
同一个产品出口到欧盟和美国可能归不同税号。要素要挂在**出货批次**上并允许从产品带默认值。

### F. 收付款与多币种结算（ERP 域，`biz_` 前缀）

**业务目标**：每笔钱都能对应到单、汇率损益算得出、账龄看得见。
外贸的钱有三处不同于内贸：**分期收（订金 + 尾款）、跨币种、跨月核销**。三处都要在模型里留位置。

| 编号 | 能力 | 要点 | 优先级 | 现状 |
|---|---|---|---|---|
| F1 | 应收 `Receivable` / 应付 `Payable` | 由订单或出货生成；挂币种、金额、到期日；支持一单多期 | P0 | 已实现：`biz_receivable` / `biz_payable`，一期一张单；应收来源暂只支持销售订单（出货来源待多币种拼柜的分摊口径） |
| F2 | 收付款单 `Payment` | 一笔收款可核销多张应收，一张应收可被多笔收款核销（核销表） | P0 | 未实现 |
| F3 | 多币种折算 | 记账金额与本币金额分列存，汇率随单据锁定，不随汇率表变动 | P0 | 已实现：报价/订单/采购/商机/货源/应收应付均按四件套存并锁汇率；只剩汇兑损益（F6）未做 |
| F4 | 账龄与对账单 | 按主体归集未核销金额，按账期分桶（30/60/90+） | P1 | 分桶已实现（T-22）；对账单待 T-29 |
| F5 | 单票毛利 | 收入 − 采购成本 − 运费杂费 − 汇兑损益 | P1 | 已实现（T-22，汇兑损益待 T-23） |
| F6 | 汇兑损益 | 收款日汇率与应收日汇率之差，单独成行，不混进毛利 | P2 | 未实现 |

**F3 的硬规则：汇率随单据锁定。** 应收单生成时把当时汇率写进单据，之后汇率表怎么变都不影响这张单。
反过来做（每次查询时取最新汇率）会让同一张单在两天里显示两个本币金额，对账时无法解释。

**F1 与 F2 为什么必须一起做**：只有应收没有核销，系统里就多了一张永远对不平的账，
业务会退回 Excel。核销表是这两者的连接件，不能拆成两个阶段。

**F6 单独成行而不是并入毛利**：汇兑损益是财务口径，毛利是经营口径。
混在一起，业务看到的"这单赚了 8%"里可能有一半是汇率波动，无法据此判断报价是否偏低。

## 五、跨模块的四条约束

这四条不属于任何单个模块，但每个模块都会碰到，写在这里避免各模块各自发明。

1. **金额一律「币种 + 金额 + 本币金额 + 汇率」四件套。**
   只存一个 `amount` 的设计在跨币种场景下必然要求回填汇率，而回填时用的汇率不是当时的汇率。
2. **单据之间的引用只存 id 与单号快照，不存对方的状态。**
   出货单上不存"订单是否已取消"，需要时去查。冗余状态一定会漂移。
3. **派生数据不加列。** 最近跟进时间、已核销金额、可用库存都从明细聚合。
   加列就要回答"什么时候更新"，答案是"每处写明细的代码都要记得"，那等于没有答案。
4. **编号分三层：案号标识生意，单号标识单据，套号标识一票货。**

   三种号各管一件事，谁也不串。**对外沟通、报关、打印、检索都用单号**；案号只回答
   "这是同一笔生意的哪一步"；套号只回答"这是同一票货"。层级不许混用——把案号当 `doc_no` 用，
   唯一索引就得放弃，而它是并发取号唯一的兜底。

   **4.1 案号 `BaseNo`：`{客户编码}{YY}{NN}-{类型}{NN}`**

   ```
   {客户编码}{YY}{NN}-{类型}{NN}       DZ2603-QT01 → 转单 DZ2603-SO01
   └──── 案号 BaseNo ────┘
   ```

   - **序号按「客户 + 年份」计**：一个客户一年一个计数器（号段键 `deal:{partner_id}:{yy}`），
     跨年从 `01` 重来。不按单据类型分号段，否则同一笔生意的报价与订单会各拿一个序号，两段号再也对不上。
   - **首件也带序号**：报价从 `-QT01`、订单从 `-SO01` 起。不要"第一份不带后缀"——
     一个号既当案号又当单据号，第二份一出现，第一份的身份就变了。
   - **转单继承案号**：`DZ2603-QT01` → `DZ2603-SO01`。
     **年份跟随案号，不跟随操作时间**：12 月报价、次年 1 月转单，号里仍是报价那一年。
   - **订单序号复制来源报价的序号**（规则，不是例子）：`DZ2603-QT02` 转出的订单必得 `DZ2603-SO02`，
     不另占一个新序号。序号在案号内按「生意」计而不是按单据计，所以同一笔生意的报价与订单
     永远同号，看号即知对应关系。
   - **直接建单取下一个未占用序号**：没有来源报价的销售订单，取该案号内当前已用序号的最大值 `+1`；
     同一案号之后新开报价也从这个号之后继续，不与它抢号。这条与上一条不冲突：
     `base_no` + 后缀的唯一性由完整组合保证，复制序号只保证 QT / SO 一一对齐，不制造重复。
   - **超 99 扩位**：第 100 笔写 `DZ26100-QT01`（不截断、不报错）；因此客户编码不得以数字结尾。
   - 案号存在独立的 `base_no` 列上，与 `doc_no` 并列，**不唯一**：报价与它转出的订单共用同一个案号，
     唯一的是「`base_no` + 后缀」这个组合。
   - 案号只覆盖报价与销售订单。采购与送货单不挂它，理由见 4.2 与 4.3。

   **4.2 采购单 `PO-{YYMM}-{NNN}`（独立号段）**

   ```
   PO-2610-001
   │  │    └── 当月序号，按月重置，上限 999
   │  └────── 建单时的年月
   └───────── Purchase Order
   ```

   - 建草稿时取号，落在 `doc_no`（`uniqueIndex`）。
   - **不挂案号**：采购对的是供应商，一张 PO 可以覆盖多张销售订单，也可能先于任何订单存在（备货）。
   - 明细行的 `sales_order_item_id` 可选，只回答"这批货是为哪张单备的"，不参与发号。
   - **不强制采购挂销售订单**：备货采购真实存在，强制挂单只会逼人先造一张假订单。
     代价是这类采购的成本要等有销售订单时才归集得到单票毛利（T-22）。

   **4.3 送货单 `DN-{YYMM}-{NNN}`（独立号段 + 套号）**

   ```
   DN-2610-001
   │  │    └── 当月序号，按月重置，上限 999
   │  └────── 建票时的年月
   └───────── Delivery Note
   ```

   - 出货批次创建（草稿）时取号，一票一号。`YYMM` 单调递增，按字符串排序与时间顺序一致。
   - **不挂案号（单票出货也不挂）**：合并出货让一票属于多笔生意，"号挂谁"无论怎么选都会说谎；
     单票出货虽然归属明确，也不能例外——同一类单据并存两种编号格式，"看号知归属"就从规则退化成
     概率事件：`DN-2610-001` 到底是不是某一笔生意的，得先查分配行才知道要不要查。
     所以口径只有一条：送货单一律不挂案号。归属由分配行回答——见下面的四场景表。
     这也是出货批次、出入库单、库存流水都不带 `base_no` 的同一个原因。
   - **同一票的送货单 / 商业发票 / 装箱单共用一个号**（套号）：

     | 文件 | 内部印的编号 | 文件名 |
     |---|---|---|
     | 送货单 DN | `DN-2610-001` | `DN-2610-001-DN.pdf` |
     | 商业发票 CI | `DN-2610-001`（`Invoice No.` 就写它） | `DN-2610-001-CI.pdf` |
     | 装箱单 PL | `DN-2610-001`（另印 `DN No.` 同号） | `DN-2610-001-PL.pdf` |

     文件内部编号必须一致：一套资料三个文件，客户与报关看到的是同一个号；区别只在文件名后缀。
     套号规则属本文（共用一个号、`-R{n}` 升版本、不单独发号）；CI / PL 上印哪些字段、模板怎么排，属 T-25。
   - **改证重开不换号，升版本**：`DN-2610-001-R1`，发票注明
     `Issued in substitution of DN-2610-001 dated 2026-10-20`。同号不同内容是唯一真正禁止的事，
     版本号是它的解药。不新增 `invoice_no` 列：由 `shipment.doc_no` + `invoice_revision` 派生，避免两个真相。
   - **一票只属于一个客户**：收货人与发票主体不同就不是一票，否则 CI 与 DN 不再 1:1。

   四类出货场景，每类都要能答出六个问题：

   | 场景 | 生成时机 | 唯一性 | 关联关系 | 可追溯性 | 并发与重复提交 | 作废与重开 |
   |---|---|---|---|---|---|---|
   | ① 分批出货（一张 SO 分三次发） | 每建一票草稿就取号（`DN-2610-001/002/003`），不等确认 | `doc_no` 唯一索引；三票各自取号，互不派生 | 三票的分配行都指向同一张 SO 的行，各自数量合计 ≤ 该行数量 | 订单侧 Σ 未取消票的分配数量 = 已出数量；任一票能反查它装了哪张单的哪几行 | 两票同时抢同一行：未出数量在服务端算、同事务校验，超出返回 409；同一请求重复提交会落第二票，确认前须核对 | 草稿可删、号不复用；已确认只能整票取消（释放占用量），不能改数量 |
   | ② 多单合并并部分出货 | 建合并票时取一个号，三张 SO 的分配行挂在同一个 `shipment_id` 下 | 一票一号；不按订单拆号（否则一张送货单印出来是三个号） | 分配行是唯一关联载体：`shipment_id` ↔ 多个 `sales_order_item_id` | 按订单看「被哪几票出过」，按票看「装了哪几张单的什么」；号只回答"哪一票" | 跨订单抢量在同一事务内校验，任一行超额则整票失败；第二张单加进同一票不换号 | 整票取消、三张单的占用量一并释放；只错其中一单的部分也走整票取消再重开 |
   | ③ 同单多次部分出货 | 每次发货新建一票并取号；订单本身不换号、不改号 | 号在票上而不在订单上；同一订单多次出货不产生订单号变体 | 订单不存"已出几票 / 已出多少"（派生数据不加列），只由分配行聚合 | 剩余量 = 订单行数量 − Σ 未取消票分配数量；「部分出货」是聚合结果，不是新状态 | 同①：上限在服务端算，本请求内同一行出现两次要累计 | 未确认的票删掉即释放；已确认的票只能取消，货已在途则走退货 |
   | ④ 合并后追加出货 | 追加时新建一票取新号，原票不动 | 新票新号，与原票并存；不复用、不把数量追加进原票 | 两张票的分配行指向同一批订单行，已出数量是两票之和 | 从订单行能看到两票；「这票是补发」目前只能写备注，正式补发关系要另立字段，不进编号 | 追加量同样受未出数量上限约束；原票已出货时不允许回改 | 新票按①②③处理，与它补的是哪一票无关——补发不改变原票 |

   **判定规则**：**原票未确认则改原票，已确认只能新开票。** 已确认的票不可撤销，
   错了做反向单（退货 / 补发），而不是把原票改小或删掉重开——那会让已经发给客户与货代的那张
   `DN` 指向不存在的数量。

   **4.4 箱唛：主标识印销售订单号**

   ```
   DZ2603-SO01                     ← 主标识，最大字号（系统生成）
   INVOICE NO.: DN-2610-001        ← 法定要素（系统生成；改证升版本时换贴纸）
   C/NO. ___/___                   ← 箱号，人工填写
   G.W. ___  N.W. ___  MEAS. ___x___x___CM   ← 毛净重与尺寸，人工填写
   MADE IN CHINA
   ```

   - **为什么印订单号而不是送货单号**：客户仓库按订单分货，箱上印订单号最直观；订单号在整票生命周期内
     不变，是箱上唯一永远成立的主标识。合并票天然可表达——两组箱各印各的单，谁也不串。
   - **发票号随版本变，做成贴纸**：改证重开升 `-R1` 时 `INVOICE NO.` 跟着变。把它与订单号一样印死在箱上，
     就等于每改一次证都要重贴整张箱唛；所以模板里订单号印死、发票号留成一枚贴纸，改证只换贴纸。
   - **系统只出「一箱一单」的唛**：模板只提供订单号与发票号两个占位，箱号、毛净重、尺寸一律人工填。
     系统不出箱明细，也就不承诺箱号连续或总箱数——分箱方案要到实际装箱时才定，先在系统里排一遍是重复劳动。
   - **混装箱人工出唛**：一箱装多张订单的货时，系统不生成箱唛，只提供"这箱用了哪些分配行、各多少"，
     排版由人工完成。为占比极低的例外做版式与排版逻辑不划算，人工还能按客户习惯重排。
   - 案号不上箱：客户若认它，印在文件的 `Our Ref.` 栏，不占箱唛版面。
   - 箱贴二维码（`DN-2610-001 / C-0007`）依赖箱明细，本次不做。

   **4.5 成组锚点与互引**

   一套资料靠三个锚点互认，不靠"同号"：① `Invoice No.`（= 套号，报关的法定申报要素，也是对外主键）；
   ② `B/L No.`（同一票货的运输标识）；③ 唛头 / 箱数 / 毛净重 / 品名与 HS（逐行比对）。

   因此三份文件必须互引，拿任意一份都能找到另外两份：

   | 文件 | 必须印 | 作用 |
   |---|---|---|
   | 商业发票 CI | `Invoice No.` + `Delivery Note No.`（同号）+ 全部 `Your Order No.` | 对外主键；指向票与订单 |
   | 装箱单 PL | `Invoice No.` + `DN No.` + 箱号区间 + 箱数 / 毛净重 | 与发票对得上；用箱数逐行核对 |
   | 送货单 DN | `Invoice No.` + 全部 `Your Order No.` | 客户签收用；指向发票与订单 |
   | 箱唛 | 销售订单号（主）+ `Invoice No.`（贴纸）+ 人工填写的箱号与毛净重 | 客户按订单分货；只有前两项由系统生成 |

   **同号规则**：同一票的 DN / CI / PL 共用一个套号（这是要求，不是漏洞）；**不同票不得同号**；
   同一套号的不同版本必须带 `-R{n}`。禁止「同号不同内容」——同号不同内容比没有号更难查，因为它看起来是对的。

   **外部号**：提单号、报关单号、DO 号由外部给定，只记录字段，不参与发号与唯一性。

   **命名边界**：实体仍是出货批次 `Shipment`，`DN` 是它的单号，不新增"送货单"表；
   `DN`（我方送货单）≠ `DO`（货代或船公司的提货单）。

   **4.6 三种号共用的规则**

   - **不查最大号 +1**：两个并发请求会拿到同一个号，撞的是唯一索引，表现为保存失败而不是重试。
   - **号不回收**：删掉的号已经出现在邮件、报关资料和聊天记录里，重发一次就有两个单指向同一个号。
   - **到上限报错，不扩位**：`PO-` / `DN-` 每月 999 用尽时返回明确错误并提示扩宽号段，不静默变成 `1000`。
     理由是段宽而不是"号码太长"：`{NNN}` 是定长 3 位的段，它撑着三件事——按字符串排序等于按时间排序、
     解析时定长切片、号段键 `(doc_type, period)` 与号码一一对应。某个号自己变长，三件事同时失效
     （`PO-2610-1000` 按字符串排在 `PO-2610-999` 前面），而失败又是静默的。
   - **段宽是常量，扩宽是一次迁移**：`PO-` / `DN-` 的序号段固定 3 位，真要扩到 4 位就改这个常量、
     同时调整存量号码，不让单个号自己变长。案号是唯一例外：同一笔生意的号必须能继续，
     所以 99→100 时扩一次（`DZ26100-QT01`），且只扩这一次——段宽从 2 位到 3 位后不再回头。
   - **号段 period 存 `YYYYMM`、展示 `YYMM`**：存 4 位年，2100 年才不会与 2026 年撞到同一行。
   - **其余单据**（`IN-` / `OUT-` / `CT-` / `MV-`，以及未建表的 `RC-` / `PY-` / `PM-` / `CD-`）暂按代码现状
     `{类型2字母}-{YYYYMM}-{4位流水}` 发号；T-47 一并统一为 `{YYMM}-{NNN}`，避免多种格式长期并存。

## 六、刻意不做的范围

与根 `AGENTS.md` 第 1 节的清单一致，这里只补与外贸相关、容易被顺手加上的几条：

| 不做 | 原因 |
|---|---|
| 报关单一键对接单一窗口 | 各口岸接口与授权差异大，投入产出比在这里最差；先做人工录入 + 附件 |
| 自动抓船公司轨迹 | 同上，且船公司数据质量不稳定；先做人工填节点 |
| 退税计算 | 退税率随政策与商品码变动，且各口岸口径不同；先做费用录入，算在单票毛利里 |
| 信用证 / 托收等结算工具的全流程 | 只有少数大额订单用；先做"结算方式"字段 + 附件，不做单据流 |
| 客户门户 / 对外报价链接 | 需要独立的鉴权与外网部署，属于另一个产品形态 |

## 七、与主流系统的功能对标

**本节只保留判断结论。** 逐模块的现状、证据与差距判定在 `docs/gap-analysis.md` 第三章，
对标来源与抓取日期在那一章的 3.1。

对标对象按品类分四类，只取与本项目同阶段（中小外贸公司、自营出口、代理采购）的部分：

| 品类 | 代表 | 它的强处 | 不值得照搬的部分 |
|---|---|---|---|
| 专业外贸 CRM | 小满 OKKI、孚盟 MX、富通天下 | 邮件与 WhatsApp 往来归档、公海池、查重、单证与 PI 一体 | 邮件集成需要 IMAP 与合规授权，且依赖具体邮箱商 |
| 通用 CRM | Salesforce、Zoho、HubSpot | 销售漏斗、业绩目标、自动化提醒 | 表单与流程引擎过重，外贸特有的单据与报关它不管 |
| 通用 ERP | SAP B1、Odoo、ERPNext | 库存与财务的正规性、多币种核算 | 报关与单证是外挂模块，落地成本高 |
| 单证 / 物流工具 | 单一窗口、报关软件、货代 TMS | 报关要素库、舱单与提单对接 | 接口按口岸授权，一家一个样 |

### 差距里最要紧的三条

1. **没有单据与 PDF（G）**：系统的价值在"能对外交付一份东西"。没有 PI 与发票，业务就得在
   Excel 与系统之间来回抄，抄错一次是钱。
2. **没有报表（H）**：只要老板还在 Excel 里算毛利，系统就永远是副账；报表口径必须与单据同源。
3. **没有数据范围（I）**：能看全部就意味着成本价与毛利对所有人公开；等到数据量大了再补，
   等于洗全表。

### 结论：缺口集中在 G / H / I，不打断主链

三组都是 P1～P2，排在阶段 7～9（客户 → 报价 → 订单 → 出货 → 收款 之后）。
唯一例外：**业务确实要求「先出 PI 再签单」时，T-24 可提前到阶段 3 末尾**。

另有 10 个横切任务（T-37～T-46：金额定点化、出货入库存、信用拦截、客户查重、事务边界等）
来自差距分析，它们不是新能力而是补现有能力的地基，排期见 `docs/roadmap.md` 阶段 5.5 与各阶段行。
