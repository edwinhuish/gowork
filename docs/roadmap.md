# 实施路线

**职责**：全项目**唯一的任务表**——编号、交付物、验收标准、依赖、优先级、进度，都只在这里维护。
**不管**：为什么需要这个能力（`docs/trade-erp-crm-blueprint.md`，下文用能力编号 `A1` / `B2` 引用它）、
差距证据与重构理由（`docs/gap-analysis.md`）、业务对象命名（`docs/glossary.md`）。
**相关**：`docs/gap-analysis.md` 第七章给出 T-37 起的任务「为什么建议做、建议插在哪」，本文只记结论与验收。

## 一、排期原则

1. **沿业务主链推进，不按模块难度推进。** 先把"客户 → 报价 → 订单 → 出货 → 收款"接通，
   再回头补字段。链条断在哪，系统就会被 Excel 顶替。
2. **底座先行，且只做一次。** 币种、汇率、单据状态、单号这四件事被后面每张单据引用。
   先各模块自建一套，事后统一的成本是"改全部表 + 洗全部历史数据"。
3. **一个任务一次提交，且必须是可验证的完整切片。** 后端接口能往返、前端页面能操作、
   `task lint` 与 `task test` 通过，三者齐全才算完成。半截的中间态不提交。
4. **P2 不阻塞主链。** 遇到"顺手就能加"的 P2 能力，记在这里而不是当场做。
5. **对标补强不插队。** 阶段 7～9 是照主流外贸系统补的（单证、报表、数据范围），
   全是 P1/P2，排在主链之后。唯一例外是 T-24（PI）：若客户要求"先出 PI 再签单"，
   它可以提前到阶段 3 末尾，那时报价与订单的数据已经够用。

**T-47 为什么排在阶段 3 收尾（P1）**：案号 `{客户编码}{YY}{NN}` 标的是「一笔生意」，得等报价 → 订单 →
采购三段都在（T-10～T-13）才有东西可串；而一旦有了真实数据再改号，就要连带重编历史单。
它**不动号段机制**（`sys_doc_seq` 的 `(doc_type, period)` 不变），只把格式换成 `{YYMM}-{NNN}`、
让报价与订单从案号派生，并给送货单补上套号与箱唛。细则见蓝图 §五.4。

**T-47 已做到号与套号**：`base_no` 落库、报价与订单按 `{案号}-{类型}{NN}` 发号、
转单沿用来源的案号与序号（QT03 → SO03）、序号用尽报错不扩位（案号 99、三段式 999）；
采购与送货单改 `{类型}-{YYMM}-{NNN}`、`SH-` 重编为 `DN-` 并留下
`sys_doc_no_rename` 新旧对照、号段同步推到重编后的最大值；
送货单落 `invoice_revision`；跨客户合并一票返回 400。
**T-47 已完成**：号与套号两层都落地。CI / PL 与送货单共用套号的文件名与打印件随 T-25 补齐
（`-CI` / `-PL`，改证带 `-R{n}`，`POST /shipments/:id/reissue` 升版本），箱唛随最后一批收口。

**箱唛的两条口径**：一是只出「一箱一单」版式——订单号印死（客户仓库按订单分货，订单号在整票
生命周期里不变），发票号留成一枚贴纸位（改证升版本只换贴纸，不重贴整张唛），箱号、毛净重、
尺寸一律留白给人工填（分箱方案要到实际装箱时才定，系统先排一遍是重复劳动，排错了还得跟着改）；
二是混装箱（一箱装多张订单的货）系统不生成唛，只提供"这箱用了哪些分配行、各多少"的明细，
排版由人工完成——为占比极低的例外做版式逻辑不划算（§五.4.4）。

**T-48 只服务检索**：它不给任何单据加字段、不动 `doc_no`，做完的效果只是"客户报一个旧编号也能找到产品"。
所以它不改变主链顺序，也不与 T-47 的单号改造重叠——两者唯一共同点是都必须保证"词能查到单/货"。

**T-48 已完成**：`md_product_code`（`code` / `code_norm` / `source`）+ `/product-codes` 增删查 +
产品列表关键词并入编号（子查询，不是 JOIN）+ 改 SKU 自动沉淀旧码 + 列表项 `matched_codes`。

**T-48 收尾补的两处**：一是**供应商货号不复制进编号表**——它跟着供应商与采购价走，真相在
`md_product_source.supplier_sku`，另存 `supplier_sku_norm` 参加同一次关键词检索（存量由
migrate 回填），复制一份到 `md_product_code` 就成了两处真相，改价时得记得同步两遍；
二是**单据里的产品下拉改成按关键词远程搜**（`components/product-select.tsx`）——原来一次取满
200 条在前端过滤，产品过两百条之后后半段选不到，客户报的编号也过滤不出来，
而这恰恰是要靠后端按编号查的场景。

**T-48 的三条口径**：一是一张**单独的编号表**而不是给产品加几个字段——同一件货可能有三家客户
各给一个物料号，固定几列到第四个客户就不够用；二是**归一化落库**（`code_norm`，转大写、去空格
与连字符），查询时关键词走同一个函数，一边归一化一边不归一化就会出现"明明有却搜不到"；
三是编号**并进关键词条件走子查询**——一个产品能命中多个编号，JOIN 会让它在一页里出现好几行，
`count` 也跟着变大。同一产品内归一化值唯一（409），跨产品允许共用（两家客户从同一工厂拿货）。

**T-45 已完成**，三块一起做：

一是**唯一键冲突翻译成 40901**，翻译放在 `database.Open` 注册的 gorm Create/Update 回调里——
写入出口有 Base 的通用方法、各仓储自己开的事务、事务里的 `tx.Create` 三条路，逐个调用点翻译
必然漏一处，漏掉的那处会表现成"偶尔保存失败，刷新一下又好了"。

二是**删产品时清掉它的编号**，并让 `ExistsNormAnywhere` 排除软删产品的编号，否则孤儿编号
没有任何入口能删掉，却永久占着那个号。

三是**软删除改用整数标记**（`soft_delete` 插件：未删 `0`、删除 Unix 毫秒），唯一索引一律改成
`(业务列, deleted_at)`，即"未删才唯一"。原来 `gorm.DeletedAt` 用 NULL 表示未删除，而 NULL 在
唯一索引里互不相等——"同一编码只能有一行未删除"在数据库层根本落不下去，删掉产品后同 SKU
建不回来，前端只能报"编码重复"。存量库由 `database.AutoMigrate` 内嵌的 `prepareSoftDelete`
自动升级（先删旧索引、再把 timestamp 转成毫秒），三库各有用例覆盖。

规范见 `apps/backend/AGENTS.md` 的「软删除」一节，取舍理由见 `docs/architecture.md` 第 7 节。

**T-29 已完成**：`GET /reports/collection` + 页面 `/collection`。要点：

- **回款率是流量，超期明细是存量**，两者放在一页但不互相校验。分子按**到账日**

- 分子两个条件都带（资金方向 + 目标类型）：只按方向统计会把**预收**（还没对应任何单据的钱）
  也算成回款。

  `UpdateWithTerms`），两条路径共用 `takeOptimisticLock`；用例覆盖两条路径各一次。

- **收尾审计（POST 逐个过一遍）**：八个新建页走 `useForm` 带键；T-44 的

  换个键立刻多出一条——说明去重是按意图生效的，不是整个接口不落库。

**T-36 已完成**：成本价与毛利对业务员隐藏。要点：

- **清在服务端**：四处（产品列表 / 详情、单票毛利、销售看板、产品毛利下钻）在返回前
  把 `cost` / `charge` / `profit` / `margin` 清成 0，并带 `cost_hidden`。

- **收入与订单额照给**：业务员要知道自己卖了多少，只是不知道赚了多少。
- **清成 0 而不是省略字段**，并且必须配 `cost_hidden`：省略会让前端显示 NaN；
  0 不配标记，"看不到"与"这件货不要钱"在界面上就分不开——两者含义正好相反。

**T-34 已完成**：`GET /reports/todos` + 页面 `/todos`。要点：

**T-33 已完成**：`sys_audit_log` + 写操作统一留痕 + `GET /audit-logs`（管理员）+ 页面 `/audit-logs`。要点：

- **记在中间件，不在各 service 里**：漏一处就等于那类单据没有留痕，而"哪几类忘了记"
  在出事之前没人会核对。挂在 `secured` 组上，新增任何写接口自动被覆盖。
- **记的是提交意图，不是前后 diff**：请求体 + 路由 + 状态码。真 diff 要在每个 service

- **动作取路由里 `:id` 之后那一段**（`status` / `merge` / `restore` / `changes`），
  不是笼统的 `update`——翻日志的人找的就是这个动作。集合级写操作没有 `:id`，`entity_id` 记 0。
- **不可改靠"没有方法"**：仓储只有 `Create` 与 `List`，表不嵌 `Base`、没有 `updated_at` /

- **失败的操作也记**：4xx / 5xx 同样是"发生过的事"，403 更是安全信号。
- **脱敏按键名片段、按字符截断**：`new_password` / `oldPassword` 这类写法一定会出现；
  按字节截会把多字节字符切成非法 UTF-8。multipart 不读，只记一句摘要。
- **写失败不拦业务**：请求已经落库并返回，回滚等于"成功却报失败"；改为应用日志留 warn。
- **T-39 的强制放行与 T-41 的合并由此一并覆盖**（`force_credit` / `source_id` 都在请求体里），
  不再需要各自单独接一次审计。

**T-32 已完成**：角色扩展 + `md_partner.owner_id` + 查询范围 + 转移入口。要点：

- **三个角色**：`admin`（全部数据 + 系统设置）/ `manager`（全部数据，不碰系统设置）/
