## 一、结论摘要

### 1.1 当前最要紧的三条缺口

上一版的三条致命缺口（钱没闭环、没有对外交付物、没有数据范围与审计）已被 T-20～T-48 全部关闭。
本轮按代码重扫，**没有发现新的链路断点**：线索 → 报价 → 订单 → 采购 → 出货 → 出库 → 应收 →
收款核销 → 账龄 / 毛利是一条能跑完的闭环。剩下的问题集中在另外三类——

| # | 缺口 | 为什么最要紧 | 现状证据 |
|---|---|---|---|
| 1 | **单证要素不足**：主体只有单列 `address`、无税号；出货票上没有收货人 / 通知方 / 货代；产品无箱规与单件毛净重 | 外贸一张单证上有三种地址（发票抬头 / 收货人 / 通知方），业务假设第 6 条明写「报关资料、发票抬头、付款主体常常不是同一个人」。现在 CI 与 PL 只能取到同一个地址，订舱要的 CBM 只能人工算——这不是「功能不完整」，是**打印出来就错的单子** | `model/partner.go:136-188`（单 `address`，无 `tax_id`、无多地址）；`model/shipment.go:14-43`（只有 `bl_no/vessel/etd/eta`，无收货人 / 通知方 / 货代）；`model/product.go:9-65`（无箱规、无单箱毛净重 / 体积）；`service/pdf.go:31-42`（5 种模板，无装船通知 / 产地证 / 保险单 / 订舱委托） |
| 2 | **更正只有「删单」一条路**：核销不可反冲、应收应付只能作废、出货不可撤销、出入库单无红冲、杂费只能删 | 客户退一半货、货代退款、报关改单重报，是外贸每周都会发生的事。系统里表达不出来，只能删掉原单——单号消失，客户手里那份对不上，审计里只剩一条「删除」 | `service/payment.go:134,240-244`（"要撤销核销请删掉整张收付款单"）；`service/receivable.go:117-124`（有核销后禁改禁删，只能作废）；`model/document.go:62-63`（已出货不可回取消）；`service/stock_document.go:158-161`（提示做反向单，但没有反向单接口）；`service/shipment_charge.go:139-141`（负数被拒，只能删） |
| 3 | **采购的收货与验货没有单据**：只有 5 个时间节点，没有收货单、没有验货结论；采购入库要手工建单，与采购订单只靠一个字符串关联 | 代理采购卖给客户的是「我验过货」。验货只有 `done_date`，没有结论、缺陷项与照片，出了问题无法自证；入库单的 `source_doc_no` 是人填的，填错就追不到是哪张采购单 | `model/purchase_milestone.go:15-19,72-89`（节点只有计划日 / 完成日 / 操作人）；`model/stock_document.go:108-128`（`source_doc_no` 为字符串，无外键）；全仓 `GRN\|收货单\|验货报告\|RMA` 无模型 |

三条的共同点：**主链不缺步骤，缺的是每个交接点上那张能对外、能反悔的凭证**。
阶段 10 的任务全部由此派生——不是补新模块，而是给已有链路补文书、补反向凭证、补档案要素。

### 1.2 最该先动的三件事

| 顺序 | 动作 | 理由 | 关联任务 |
|---|---|---|---|
| 1 | **主体多地址与外贸档案字段** | 它同时被 PI、商业发票、装箱单、报关单、订舱委托五处引用。晚做一次，五套模板各改一遍；而地址是 1:N，塞进主表就再也拆不开 | T-49 |
| 2 | **红字单据体系**（贷项通知单 + 采购退货 + 出入库红冲 + 核销反冲） | 这是钱的更正路径，也是审计链的完整性。它与第一件无依赖，可并行；但必须早于「按出货开票」（T-53），否则开票口径一改，冲销要重写 | T-52 |
| 3 | **采购收货单与验货记录** | 收货单是「采购订单 → 库存」之间唯一还缺的那张单。补上之后，在途量、未收数量、验货结论才有落点，也为批次追溯（T-58）留出挂点 | T-51 |

**用户管理（T-57）不在这三件里，但它有独立的时间压力**：现在只有 `GET /users`，
换人或离职只能改数据库；而角色写在 JWT 里，改完还要等令牌过期才生效。团队里出现第二个人的那天，
这件事就是运维事故。它工作量小（一张维护界面 + 三个接口），建议与 T-49 同批做掉。

### 1.3 一个被低估的二级风险：单据横向一致性

订单、采购、出货、出入库四套单据各自实现了一遍「状态机校验 + 单号 + 金额汇总 + 明细增删」。
现在口径一致（都走 `service.checkDocumentTransit` 与 `DocNoService`），但**金额汇总与明细装配仍是四份代码**
（`buildItems` 在 `sales_order.go` / `purchase_order.go` / `quotation.go` / `stock_document.go` 各一份）。
只要有一份在改动时漏了舍入，四张单据的合计就会出现「差一分」，而对账时最难解释的就是一分。

T-37 把金额换成了定点 `Decimal`，浮点尾巴这一层风险已经消除；但**装配逻辑本身仍是四份**。
新增反向单据（T-52）时会再写第五、第六份：反向单的金额要取反、数量要取反、来源要回填，
每多一份就多一处可能算错的地方。建议在 T-52 动工前先把「明细装配 + 金额汇总」收成一个函数，
这是本项目里少数几件「先重构再开发反而更快」的事。

### 2.3 完全未实现

代码里连「记录」都不存在的业务对象，只剩下面这些——它们不是某个模块的字段缺失，
而是整类能力没有载体：

- **主体侧**：客户分级（ABC）、公海池与回收规则、多地址实体、税号与海关编码。
- **销售侧**：价格表 / 客户等级价 / 阶梯价、销售佣金、样品单。
- **采购侧**：询价单（RFQ）/ 供应商比价、收货单（GRN）、验货报告、采购退货。
- **库存侧**：仓库与库位、批次 / 序列号、ATP 可承诺量、库存估值。
- **单证侧**：装船通知、产地证、保险单、订舱委托，以及这些单证的打印件。
- **财务侧**：对账单、贷项 / 借项通知单、红字收付款、期末汇率重估、合同分期回款状态。
- **系统侧**：通知中心、自定义字段与字典表、多语言、时区。

**注意「完全未实现」不等于「该做」**：上面有六项属于明确不做（见第九章），
另有四项缺业务口径（见 `docs/roadmap.md` 第五节），立卡前要先定口径。

### 3.3 矩阵读法

四条容易误判的行，单独说明：

1. **「部分覆盖」占了 30 行里的 20 行，这不是坏消息**。主链已通，剩下的绝大多数缺口是
   「再走一步就完整」：加一张表、加一个字段、加一个出口。真正要从零建模块的只有
   仓库维度、批次追溯、价格表、客户分级四类。判断一条缺口值不值得做，先看它属于哪一类——
   「补齐」通常一两天，「新建」通常一周起。
2. **「客户分级与公海」判缺失但标 P2，且不立卡**：缺的不是代码是口径。按成交额分级，
   淡季开发的新客户会被判成 C；按毛利分级，要先定义毛利含不含运杂费；按回款速度分级，
   又要有人定期重算。没有一条能在不访谈业务的情况下定下来，立卡等于先编一个规则。
3. **「多语言 / 时区」判缺失但只到 P2**：界面多语言是产品形态问题（客户是境内业务员，
   全部用中文），真正有业务价值的是**单据输出语言**——CI / PL 给海外客户看，
   现在只能印中文品名。所以这一条应拆成两半，只做后半（见 T-64）。
4. **「多法人 / 多租户」判缺失但不进任务表**：真实需求通常是「多份部署 + 各自独立库」，
   而不是一个库里装多个租户。侵入点与成本见第六章，排除理由见 9.3。

### 4.3 库存与采购

#### 现状

- **流水是事实、快照是缓存**：同事务写入，快照用 `ON CONFLICT ... qty = qty + ?` 原子加，
  另有全量重算作为对账手段。允许负库存（直发业务常态）。
- **确认才产生流水**：草稿改多少次都不动库存；确认后不可撤销，提示「做一张反向单」——
  但反向单接口还没做，实际只能人工新建一张方向相反的单据。
- **手工流水只放行期初 / 盘点盈亏 / 其它**，采购入库与销售出库必须挂单据。
- **采购价不从货源表取**（有意：采购价是谈出来的），汇率独立锁定，以销定采三项校验。
- **无仓库、无库位、无批次**；调拨类型编号已占但主动 400。
- **采购跟单节点已做**（T-38）：五个节点挂在订单行上，计划日与完成日分开，逾期可筛。

#### 缺失点

1. **没有收货单**。采购订单 → 库存之间靠人手工建入库单，`source_doc_no` 是字符串。
   后果有三：在途量算不出（不知道还有多少没到）、入库单追不回采购单、分批到货只能建多张互不关联的单。
2. **验货只有时间戳**。`biz_purchase_milestone` 的「验货」节点只有计划日 / 完成日 / 操作人，
   没有结论、缺陷项、抽检比例与照片。代理采购卖给客户的核心承诺是「我验过」，这一点无法自证。
3. **单池模型撑不住「备货 + 直发」并存**。两者共用一个产品维度的池子，
   「这个 SKU 还能卖多少」算不准；调拨因此只能拒绝。
4. **没有批次追溯**。客户投诉某一批货，追不到是哪张采购单、哪个供应商、哪次验货。
5. **运杂费只归集到票面**。报表按收入占比摊到行，拼柜时高价值小体积的货背走多数运费，
   按产品看的毛利会失真。
6. **盘点差异没有原因分类**。差异直接生成流水，事后无法按漏录 / 损耗 / 错发统计。

#### 改进建议

| 建议 | 任务卡 | 说明 |
|---|---|---|
| 采购收货单（挂采购订单行、支持分批、生成入库流水）+ 验货记录（结论 / 缺陷 / 附件） | T-51 | 收货单是三个挂点：库存、在途、验货 |
| 仓库与库位（快照唯一键改 `warehouse_id + product_id`），随之开放调拨 | T-56 | 触发条件已满足：备货与直发已在同一池子里混着 |
| 批次 / 序列号（流水与快照加维度，收货单与出货分配行带批次） | T-58 | 依赖 T-51 与 T-56 |
| 运杂费分摊依据（按体积 / 重量 / 柜 / 行，可配置） | T-59 | 与收入占比并存，按票选择 |
| 盘点差异原因枚举 | 并入 T-56 | 加一个字段，不改结构 |
| ATP 可承诺量 | 不立卡 | 依赖 T-56 与 T-58，口径见 `docs/roadmap.md` 第五节 |

### 4.4 多币种结算

#### 现状（底座与四件套都成立）

- **底座是对的**：唯一本币、汇率只追加、按生效日半开区间取、缺汇率直接 400
  而不是把 0 写进本币金额。`Convert` 是唯一折算函数，没有第二处实现。
- **四件套覆盖 8 张表**：报价单、销售订单、采购订单、商机、产品货源、应收应付、收付款、
  运费杂费；报价明细额外存「原币 + 本币」两列。
- **汇率在 service 写入时锁定**（`service/document.go:59-85`），收款按到账日汇率，
  差额逐笔落成汇兑损益表（`/reports/exchange-gains`）。
- **金额已定点化**（T-37）：`money.Decimal` = int64 × 1e-6，接口以十进制字符串收发，
  派生的「结清 / 超收 / 可出量」判断不再留容差。

#### 缺失点

1. **没有期末重估**。未核销的外币余额按期末汇率重新估值这一步没做——已实现的汇兑损益
   只覆盖「已核销」的部分，账面未实现损益仍按历史汇率计。
2. **单一汇率，没有买入 / 卖出价**。银行卖美元给你的价与买你美元的价不同，

3. **商机按当日汇率重算**（`service/opportunity.go:237-250`），加权预测随汇率漂，
   季度环比失去可比性。
4. **前端金额固定两位、不带币种符号**（`components/fields.tsx:20-32`）。
   后端按币种小数位舍入，前端 `minimumFractionDigits: 2` 写死——JPY 显示成 `1,000.00`，
   KWD 的第三位被截掉；混币种列表里也认不出这是哪一国货币。

| 期末重估：按指定日汇率重算未核销余额，差额单列一张报表 | T-60 | 与汇兑损益分开，不并入毛利 |

| 成本与毛利在服务端清 0 并带 `cost_hidden`，覆盖产品列表 / 详情、单票毛利、销售看板、产品毛利下钻 | `service/cost_visibility.go:38` |
| 审计挂在 `secured` 组，全部写方法自动留痕（含动作、状态码、脱敏请求体） | `middleware/audit.go:42-89` |
| 账号目录 `GET /users` 只列启用账号，业务员 403 | `router.go:115`；`service/user.go:11-35` |

#### 缺失点（按风险排序）

1. ~~没有用户维护~~ **已修（T-57）**。建号、改角色、停用、重置密码有了 `/user-accounts`
   三个接口与一个页面；最后一名管理员不能被停用或降级，自己也不能改自己的角色与状态——
   系统里没有「恢复出厂账号」的入口，进了那个状态只能改库。
2. **路由级授权只有一处**（`/audit-logs`）。其余 180 条路由都是「登录即可」，
   角色差异藏在 service 里：前端无法据路由判断某人有没有这个入口，
   新加接口时也容易忘记补 service 里的判断。
3. ~~角色写在 JWT claims 里，改角色在令牌过期前不生效~~ **已修（T-57）**。会话值里带签发时间，
   账号变更时记一个「此刻之前签发的令牌作废」的时间戳，校验时会话签发时间不晚于它即拒绝。
   没有改成每次请求查库：那样每个请求多一次主键查询，而吊销戳只在变更时写一次。
   老格式会话（只存 uid）认不出签发时间，一律放行到自然过期——为这一点把所有人踢下线不值得。
4. **登录 / 登出不在审计里**。审计只覆盖 `secured` 组的写方法，谁在什么时候登录、
   从哪个 IP 登录、失败了几次，只有应用日志，没有可查询的视图。
5. **附件面板只挂了 3 个页面**（出货、客户、供应商）。后端 12 类实体可挂，前端入口不足，
   等于大部分附件能力用不上。

#### 改进建议

| 建议 | 任务卡 | 说明 |
|---|---|---|
| 用户维护：建号 / 改角色 / 停用 / 重置密码，停用即吊销该用户全部会话 | T-57 | 不需要角色表，三个常量够用 |
| 附件面板铺到其余单据详情页 | T-63 | 纯前端挂载，后端已支持 |
| 路由级授权逐步铺开（先写类接口，再读类） | 不立卡 | 先定「哪类角色能写哪类资源」，定完再一次改路由表 |
| 登录 / 登出进入审计 | 并入 T-57 | 与用户维护同一批，都是账号生命周期 |

## 五、架构评估

### 5.1 分层与依赖方向

**结论：方向正确，是这套代码最扎实的部分。** `handler → service → repository → model` 单向，
`service` 不碰 gin、`handler` 不碰 gorm，有 `go list` 自检命令可验证（`apps/backend/AGENTS.md:84-91`）。
泛型 `Base[T]` + `Scope` 把分页 / 计数 / 软删 / NotFound 收敛掉了，新增模块不用重写这套易错逻辑。

**与外贸场景不匹配之处**：分层是对的，但**缺一层「单据引擎」**。外贸系统的复杂性集中在单据上：
状态机、单号、金额汇总、明细增删、审批、留痕、打印。现在这些散在 4 个 service 里各写一遍
（见 1.3）。单据类型还会继续加（合同、应收、应付、收付款、报关单——至少 5 张），
每加一张就多一份复制。

**重构方向**：不做大重构，只抽两件：

1. `service/document.go` 扩成单据公共能力（状态机 + 单号已是公共的，再加「明细装配 + 合计校验」）。
2. `repository.Base.WithTx` 接入（见 5.1 的事务问题）。

**代价与风险**：抽公共装配函数要动 4 个 service 的 `buildItems`，每个都有测试覆盖
（`quotation_test` / `sales_order_test` / `purchase_order_test` / `stock_document_test`），
风险可控，约 1 人日。

**更严重的一处：跨仓储写操作没有事务。**

`WithTx` 存在但**全仓无调用点**（`repository/base.go:56`），事务全部由 repository 内部的
`db.Transaction` 自持，service 层拿不到事务句柄。后果是两处跨服务写操作只能靠补偿：

| 位置 | 现在的做法 | 失败后果 |
|---|---|---|
| `service/quotation.go:389-413` 转单 | 先建订单，再条件更新报价；更新失败就删掉刚建的订单 | 删订单也可能失败 → 留下没人认领的草稿单 |
| `service/lead.go:228-248` 线索转主体 | 先建主体，再标记线索；失败只记日志 | 留下孤儿主体（日志里有，列表里没有线索指向） |

现在能接受，是因为这两处的失败窗口极窄。**但应收应付落地后，「生成应收 + 回写订单」会变成
每天几百次的批量动作**，补偿式写法会开始漏。建议在 T-20 之前把 `TxManager` 做出来（T-42）。

### 5.2 模块划分（按层 vs 按域）

**结论：按层分包仍然正确，但按文档自己定的触发条件，切分点已经到了。**

`docs/architecture.md` 第四节第 8 条写明触发条件是「CRM 侧模块超过三个，或出现只属于一侧的
复杂逻辑」。现状：CRM 侧已有 `contact` / `activity` / `lead` / `opportunity` **四个**模块；
ERP 侧有 `quotation` / `sales_order` / `purchase_order` / `shipment` / `stock` / `stock_document`
六个 —— 条件按其自身标准已满足。

**但我的结论是「暂不按域拆目录」**，理由是拆的收益此刻低于成本：

- 目录拆分只解决「文件多」，不解决「改动同步」。报价、订单、出货的改动天然是同步的
  （加一个单据字段，四处都要动），按域拆反而把一次改动的 diff 摊到四个目录。
- 真正的痛点是 **service 之间的调用关系**：`quotation → sales_order`、`lead → partner`、
  `product_source → currency`。这个用目录治不了。
- 拆目录的代价是 19 个 model、20 个 repository、20 个 service、18 个 handler 的 import 路径全改，
  diff 巨大而行为零变化，评审时看不出来任何东西。

**替代方向（建议采纳）**：用**编译期约束**代替目录约束 —— 在 CI 里加两条 `go list` 断言：

```
service/erp 不得 import service/crm 的包   （方向：交易不反向依赖关系）
repository 不得 import service              （已有）
```

以及在 `bootstrap` 里显式声明依赖方向注释（现在已有一份装配顺序注释，`bootstrap/app.go:119-170`）。

**真正的切分触发条件**（写死在这里，避免以后又争论）：

1. 出现**跨域的报表查询**（如「按客户统计毛利」要 JOIN 订单、出货、应收、跟进四张表）——
   这时需要的不是拆目录，而是**独立的报表层**（`service/report`）与只读模型。
2. 团队超过 3 人并行改 ERP 与 CRM —— 目录冲突开始变成真实成本。
3. 某个域要独立部署（基本不会发生，见根 `AGENTS.md`「不做微服务」）。

### 5.3 数据模型

**结论：主数据与单据的骨架是对的（主表 / 明细 / 分配表 / 流水 / 快照五类齐备）。
上一版列的 3 处硬伤已修 2 处，4 处结构缺口已补 2 处。**

硬伤：

| # | 问题 | 证据 | 后果 | 状态 |
|---|---|---|---|---|
| 1 | 金额与汇率全是 `float64` | 曾是 11 个 model 文件 + 31 处手工舍入 | 分账、核销、汇兑累计误差 | **已修（T-37）**：`money.Decimal` = int64 × 1e-6，派生判断不再留容差 |
| 2 | 软删除 × 唯一索引互斥 | 除 `sys_doc_seq` 外所有 `uniqueIndex` 表都嵌过 `DeletedAt` | 删掉产品后无法用同一 SKU 重建；冲突走到 DB 变成 500 | **已修（T-45）**：唯一索引改为 `(业务列, deleted_at)`，标记用整数毫秒 |
| 3 | 派生数据与事实数据混放的风险点 | 目前守得住（无「最近跟进时间」列），但 `md_partner.contact` 已是冗余的主联系人姓名 | 一旦有人给它加同步逻辑，就会出现两个来源 | 维持现状，写进评审清单 |

结构缺口：

| 缺口 | 影响的能力 | 状态 |
|---|---|---|
| 无 `owner_id` | 数据范围、公海、业绩归属、待办 | **已补（T-32）**：归属只存在主体上，单据经 `partner_id` 继承 |
| 无通用附件表 | 提单、报关单、验货报告扫描件 | **已补（T-26）**：`sys_attachment` + 内容分表，12 类实体可挂 |
| 无仓库 / 批次 | 备货、调拨、追溯、ATP | 未补：T-56 / T-58 |
| 无主体地址表（1:N）与税号 | 提单地址 ≠ 发票地址、开票与报关 | 未补：T-49 |

**一个可以不改的「重复」**：五张单据主表各自重复了 `partner_id / currency_code / exchange_rate /
amount_total / amount_base_total / trade_term / status / doc_no` 八个字段。看起来适合抽一个
`DocumentBase` embed（`Base` 已经证明 gorm embed 可行）。**但我建议不抽**：
gorm 的 embed 与软删、索引、`TableName` 的交互有坑（`apps/backend/AGENTS.md:391` 记录的
「改字段名没写 column 导致数据变空」就是同一类问题），而重复这 8 个字段的成本只是「加字段时多改几处」。
收益不抵风险。

### 5.4 接口设计

**做得好的**：统一响应体 `{code,message,data,request_id}`；错误码前三位对齐 HTTP 状态码；
分页三件套职责清晰；路由表只有一处；`/customers` 与 `/suppliers` 用同一个 handler 注入角色。

**问题清单**：

| 问题 | 证据 | 建议 |
|---|---|---|
| 查询参数白名单仍靠手维护 | `providers/dataProvider.ts:33-61` 有 24 项，但后端 dto 里的 `owner_id` / `direction` / `overdue` / `base_code` 仍未收录——走 `useTable` 的筛选项会被静默丢弃 | 补白名单；更彻底的做法是由 `openapi.json` 生成，与后端同源（T-63 顺手做） |

### 5.5 可扩展性

**新增一个模块的成本（按现有模板实测）**：

## 六、权限与多租户

### 6.1 单租户方案（主推）

**目标口径**：单库、单租户、不做字段级权限矩阵；但**单租户内的数据范围必须做**（与根 `AGENTS.md`
第 1 节一致）。这一段原计划分三步，**三步都已落地**；遗留的三件事写在最后。

**已落地：角色 + 数据范围**（T-32）

- 角色是三个常量 `admin` / `manager` / `staff`，不是表。原计划六个（主管 / 业务员 / 财务 / 单证 / 只读），
  实际只落三个——理由和当初写的一样：角色语义还在变，改常量是改一行，建表则是
  「一张表 + 一个维护界面 + 一套校验」。
- 归属 `owner_id` **只加在主体上**，单据经 `partner_id` 继承；`0` 表示未分配、对所有人可见。
  这让迁移面从 23 张表缩到 1 张，代价是「单据归属」不能独立于客户存在——
  客户换人时历史单据一起跟着走，而这正是业务期望的行为。
- 范围在 repository 的 filter 层用 `OwnerScope` 注入，不在 handler 后置过滤；
  后置过滤会让分页总数算错。

**已落地：字段级脱敏**（T-36）

- 在 DTO 投影阶段清 0 并带 `cost_hidden`，不在前端隐藏。三类字段：`cost_price` / `gross_profit` / `margin_rate`。
  清 0 而不是省略，是为了不出现 `NaN`；带标记，是为了让「看不到」与「这件货不要钱」在界面上分得开。
- 脱敏清单写进 `docs/glossary.md`，避免每个模块各自决定哪个字段算「成本」。

**已落地：审计**（T-33）

- 中间件自动覆盖 `secured` 组全部写方法，失败也记，请求体脱敏截断。

**还没做的三件**：

| 事项 | 现状 | 建议 |
|---|---|---|
| 路由级授权 | 只有 `/audit-logs` 一处挂 `RequireAdmin` | 先定「哪类角色能写哪类资源」，再一次性改路由表；不要逐个接口补 |
| 六个角色的细分 | 只有三个 | 等「财务」与「单证」真的出现专职人员再拆。现在拆出来没人用，只会让判断分支变多 |
| 越权语义 | 角色切片外 404、数据范围越权 403 | 统一成 403（见 4.5 的建议），改一处错误映射即可，不动查询 |

**成本**：原估 4～6 人日；实际落地部分已含在阶段 8（T-32 / T-36）与阶段 9（T-33）里。

### 6.2 若要做多租户：侵入点、成本与触发条件

**先给结论：现在不做，但要知道代价。** 现在的架构（单进程、无共享状态、存储可替换）
**已经可以用「一套代码 + 多份部署 + 各自独立库」满足多法人**——这通常就是真实需求，
而不是「一个库里装多个租户」。

如果真要做单库多租户（SaaS 化），侵入点如下：

| # | 侵入点 | 具体位置 | 漏改的后果 |
|---|---|---|---|
| 1 | 表结构 | 23 张表加 `tenant_id`；`Base` 加字段最省事，但会让 `sys_doc_seq` 这类表也带一个无意义列 | 漏一张表 = 跨租户读到别人的数据 |
| 2 | **唯一索引全部要改** | 9 处唯一键：`md_product.sku_code`、`md_partner.code`、`md_currency.code`、`md_exchange_rate(currency,base,date)`、`biz_quotation(doc_no,version)`、四张单据的 `doc_no`、`sys_user.username`、`sys_doc_seq(doc_type,period)` | 不加租户维度 → 两个租户不能有同一个 `PART-001`；加了但漏索引 → 建单 500 |
| 3 | 唯一本币 | `md_currency` 的「唯一本币」是全局约束（停用不删除） | 全库只能有一个租户设本币 |
| 4 | 发号器 | `sys_doc_seq` 的键要加租户，否则两个租户共用号段（单号会串，客户看到别人的单号） | 单号连续性失去意义 |
| 5 | 缓存 key | `session:{jti}`、`login_fail:{username}`、`dashboard:summary` 都不含租户 | `dashboard:summary` 直接串数据（现在就已经是全进程共享） |
| 6 | 令牌与会话 | JWT claims 加 `tid`；`Verify` 校验会话与租户一致 | 换租户不重新登录 |
| 7 | 迁移与种子 | `AutoMigrate` 无租户概念；`seed.go` 的演示数据要按租户建 | 新租户开箱即脏数据 |
| 8 | 测试 | `storage_test.go` 的三库断言全部要加租户维度 | 一致性保证失效 |
| 9 | 数据迁移 | 存量数据要指定「默认租户」并回填 | 老数据全部归属不明 |

**成本估算**：结构改造 + 查询注入 + 测试补齐约 **5～8 人日**；若已有生产数据，
迁移与回归另计 **3～5 人日**，且需要停机窗口。**风险最高的是第 2 项**：唯一索引漏改不会在
开发期暴露（数据量小、只有一个租户），只会在第二个租户入驻的那天集中爆发。

**触发条件**（满足任一条再做，否则用「多份部署」顶着）：

1. 同一套代码要同时服务多家互不相关的公司，且**不愿为每家单独部署**（真正的 SaaS 诉求）。
2. 集团内多法人，且**必须在一个界面上看合并报表**（这时需要的是 `company_id` + 合并层，
   而不是完整的多租户隔离——两者不是同一件事，别混）。
3. 客户的合规要求「数据必须物理隔离」，但又不接受独立部署（自相矛盾，通常说明该谈价格而非改架构）。

### 7.3 排期建议（不改变阶段顺序，只标插入点）

```
阶段 10 · P1   T-49 档案要素 → T-51 收货与验货 → T-52 反向凭证
              T-53 结算关口（← 依赖 T-52）→ T-54 / T-55 单证
              T-56 库存维度（可与前四组并行）→ T-57 用户维护（随时可插）
阶段 10 · P2   T-58 批次（依赖 T-56 + T-51）→ T-59 运费分摊
              T-60 多币种口径 → T-61 商机与分期 → T-62 跟进与待办
              T-63 导出与附件 → T-64 单据输出语言
```

**为什么 P1 的顺序是「档案 → 收货 → 反向凭证 → 结算 → 单证」**：

- 档案要素（T-49 / T-50）排第一，是因为单证与运费分摊都读它。先做单证再补地址，
  五套模板要改两遍。
- 收货单（T-51）排在反向凭证之前，因为采购退货（T-52 的一部分）要有收货单才能引用。
- 反向凭证（T-52）必须早于按出货开票（T-53）：先有「怎么冲」，再改「怎么开」；
  反过来做，冲销逻辑要跟着新开票口径重写。
- 单证（T-54 / T-55）最后，因为它是前四项的出口——地址、箱规、HS、验货结论都在单证上汇合。

**P2 的五条不设硬顺序**，但 T-58 依赖 T-56 与 T-51，其余可随时插入。
T-57（用户维护）工作量最小、风险最低，建议与 T-49 同批做掉，不要等到有人离职。

| 完整审批流引擎（可视化流程设计器） | 真实的审批点只有三个（报价改价、订单变更、信用放行）。做引擎的成本高于做三个 `requires_approval` 标记；等第四个审批点出现再说 |
| 采购询价单（RFQ）与招标 | `[Odoo-P]` `[ERPNext-B]` 都有，但代理采购的询价发生在微信与邮件里，系统里再走一遍只会多录一次。跟单节点与收货单（T-51）才是真痛点 |
| 库存估值 / 到岸成本 / 总账 | 没有会计科目体系，做估值没有账可对。单票毛利（T-22）用「收入 − 采购 − 运杂费」就够回答「这单赚没赚」 |
| BOM / MRP / 生产工单 / 分包 | 代理采购不生产。`[外贸垂直]` 里生产模块属于制造型企业版本 |
| 单一窗口 / 船公司轨迹直连 | 蓝图第六节已列，维持不做 |
| 邮件 / WhatsApp 往来归档（IMAP 同步） | 要邮箱授权与合规评估，且绑定具体邮箱商；手工记一条跟进就够 |
| 现在就做多租户 | 见 6.2：真实需求通常是「多份部署」，成本差一个数量级 |
| 按域拆目录（`service/erp`、`service/crm`） | 见 5.2：改动天然同步，拆目录只增加 diff |
| 给单据表抽公共 `DocumentBase` embed | 见 5.3：gorm embed 与软删 / 索引的交互有已知坑，重复字段的成本更低 |

### 9.2 按业务假设排除的能力

下面这些在主流 ERP / CRM 里都是标配，放进矩阵会显得「缺口很多」，但它们**不服务
蓝图第一节那 6 条业务假设**。每条都写清「什么条件下重新考虑」——避免把「现在不做」
写成「永远不做」，也避免下次对标时再重新讨论一遍。

| 能力 | 主流代表 | 排除理由 | 什么条件下重新考虑 |
|---|---|---|---|
| 总账 / 会计科目 / 凭证 | `[SAP]` `[ERPNext]` | 本项目是业务系统不是财务系统，没有科目体系；做了也没有账可对 | 公司把财务也搬进来，且愿意配一名会计维护科目 |
| 固定资产 / 银行对账 / 预算 / 费用报销 | `[SAP]` | 与「客户 → 报价 → 订单 → 出货 → 收款」这条链无关 | 同上 |
| 库存估值 / 到岸成本 | `[Odoo-I]` `[ERPNext-St]` | 代理采购多数不持有存货所有权；估值是会计口径，不是经营口径 | 开始自持存货，且需要存货资产科目 |
| MRP / BOM / 生产工单 / 分包 | `[Odoo-I]` `[ERPNext-B]` | 代理采购不生产 | 转成工贸一体，自己安排产线 |
| HR / 薪资 / 考勤 | 通用 ERP | 与外贸链无关 | 人数过百且不愿单独买 HR 系统 |
| 多租户 SaaS | — | 真实需求通常是「一套代码 + 多份部署 + 各自独立库」，成本差一个数量级（见 6.2） | 同一套代码要同时服务多家互不相关的公司，且不接受分开部署 |
| 可视化审批流引擎 | `[SAP]` `[Zoho]` | 真实审批点只有三个，引擎成本高于三个标记 | 出现第四个审批点，或审批规则每周都在变 |
| 询价单 / 招标 / 供应商评分卡 | `[Odoo-P]` `[ERPNext-B]` | 询价在微信与邮件里完成；评分卡需要长期质量数据，现在没有采集入口 | 采购额大到需要留痕比价，或客户审计要求三家比价 |
| 单一窗口 / 船司轨迹直连 | `[外贸垂直]` | 接口按口岸授权，一家一个样；先做人工录入 + 附件 | 集中在单一口岸，且该口岸接口对本公司开放 |
| 退税计算 | `[外贸垂直]` | 退税率随政策与商品码变动，各口岸口径不同 | 有专职退税岗位，且愿意维护退税率表 |
| 信用证 / 托收全流程 | `[外贸垂直]` | 只有少数大额订单用；先做「结算方式」字段 + 附件 | 信用证结算的订单占比超过三成 |
| 电商平台连接器（Amazon / Shopee / TikTok Shop） | `[Odoo-S]` | 业务是 B2B 代理采购，不是平台卖家 | 开始做平台零售 |
| 在线报价 / 客户门户 / 电子签名 / 在线支付 | `[Odoo-S]` `[ERPNext-S]` `[Zoho]` | 需要独立鉴权与外网部署，是另一个产品形态 | 客户要求自助下单，或询盘量大到人工跟不过来 |
| 忠诚度 / 优惠券 / 礼品卡 / 订阅计费 | `[Odoo-S]` `[ERPNext-S]` | B2B 代理采购没有这些场景 | 不做 |
| AI 助手 / 自然语言查询 / 智能推荐 | `[SAP]` `[Zoho]` | 数据量与查询复杂度都还没到需要它的程度；先有 20 个口径清晰的报表 | 报表超过 20 个且口径难记，或新人上手周期成为瓶颈 |
| 移动 App | `[SAP]` | 当前是桌面办公场景；响应式页面已够用 | 验货、仓库等场景需要用手机拍照录入 |

说明立卡时没有按业务假设过滤。
