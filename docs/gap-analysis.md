## 一、结论摘要

### 1.1 三个致命缺口

| # | 缺口 | 为什么致命 | 现状证据 |
|---|---|---|---|
| 1 | **钱仍没有闭环**：收付款 / 核销 / 账龄 / 单票毛利全空 | 应收应付已能开票（T-20），但收到钱之后没有地方落账，也就核销不掉、账龄算不出、毛利只能算到「应收 − 应付 − 运杂费」的应收口径。业务仍要回 Excel 记「谁还欠多少」 | `Receivable` / `Payable` 已有 model / service / 路由（T-20）；`Payment` / `PaymentAllocation` 仍只有 `DocType` 常量（`model/document.go:135`），无 model、无 service、无路由 |
| 2 | **没有对外交付物**：PI / 合同 / 装箱单 / 商业发票 / PDF / 附件全空 | 外贸的成交动作是「发一份 PI 给客户，客户凭它付定金或开信用证」。系统里做不出来，就只能手工做 Excel，而手工那份数字与系统里的订单是对不上的 | 无 `biz_contract`、无 PDF 渲染、无通用附件表；`grep -i "\bpdf\b"` 只命中一处注释 |
| 3 | **没有数据范围与审计**：任何登录用户可读写全部数据 | 成本价、毛利率、客户联系方式对所有账号公开；谁改了价格查不到。这意味着系统只能在「老板一个人用」的规模下运行，人一多就出事 | `RequireAdmin` 已定义但**未注册到任何路由**（`server/middleware/auth.go:59`，`router.go` 无引用）；全仓 `owner_id` / `tenant_id` 命中 0；无审计表 |

第 2 条的优先级在建档时被判为 P1（`docs/trade-erp-crm-blueprint.md` G 组），理由当时成立：
主链没通则单证无处取数。**但要写清一个转折点**：第一个真实客户要求「先出 PI 再签单」时，
它立刻变 P0——这不是重排，`docs/roadmap.md` 阶段 7 已经给了「T-24 可提前到阶段 3 末尾」的例外条款。

### 1.2 最该先动的三件事

| 顺序 | 动作 | 理由 | 关联任务 |
|---|---|---|---|
| 1 | **单据横切件一次做对**：审计日志 + 附件 + 打印模板 | 这三件会被 G / I 两组共 6 个任务各自碰一遍。先做骨架（一张 `sys_attachment`、一张 `sys_audit_log`、一个模板接口），后续任务只填内容；反过来做，每个单据模块都要各写一套上传与留痕 | T-33 提前 + T-26 + T-25 |
| 2 | **金额换成定点类型（decimal）** | 现在全站 `float64`（11 个 model 文件），靠 `money.Round` 在 31 处补舍入。应收应付一旦落地，金额表翻倍，迁移面从「11 个文件」变成「20+ 个文件 + 已产生的核销记录」。这是唯一一件「越晚做越贵且不能靠加班补」的债 | 新增 T-37 |
| 3 | **把文档与代码对齐**（本文第八章） | 成本几乎为零。但现状是蓝图与后端 AGENTS 里仍有「出货未实现」「跟进未做」「只落地主数据层」这类已被代码证伪的表述——按错误基线排期，会重复实现已有功能 | 第八章工单；本次已修两处 |

### 1.3 一个被低估的二级风险：单据横向一致性

订单、采购、出货、出入库四套单据各自实现了一遍「状态机校验 + 单号 + 金额汇总 + 明细增删」。
现在口径一致（都走 `service.checkDocumentTransit` 与 `DocNoService`），但**金额汇总与明细装配是四份代码**
（`buildItems` 在 `sales_order.go` / `purchase_order.go` / `quotation.go` / `stock_document.go` 各一份）。
只要有一份在改动时漏了舍入，四张单据的合计就会出现「差一分」，而对账时最难解释的就是一分。
这属于 P2，但在 T-37 做金额类型时顺手抽一个公共装配函数，成本最低。

### 3.3 矩阵读法

三条容易误判的行，单独说明：

1. **「报价审批」标 P1 而蓝图没列**：外贸报价的典型事故是「业务员报错价」——报低了当场亏，
   报高了丢单。主流垂直软件把「折扣超阈值 / 改价 / 大额」做成审批触发条件 `[外贸垂直]`。
   本项目连审批骨架都没有，而审批是横切件（与审计同源）。建议不做完整流程引擎，
   只做「改价与超折扣留痕 + 需 admin 确认」的最小版，随 T-33 一起。
2. **「商机不锁汇率」标 P2 而不是缺陷**：商机不是单据，理论上不该锁。但既然加权预测是拿去
   给老板看的数字，它就不该随每天的汇率漂。折中做法：商机同时存「报价币金额」与「录入时本币金额」，
   预测只用后者的加权，重算按钮显式触发。
3. **「库存估值」不做**：代理采购不持有存货所有权，估值与到岸成本属于会计口径，
   本项目连总账都没有。做了也没有账可对，明确列入第九章。

## 四、关键功能深挖

### 4.1 订单全流程

#### 现状（链路已通，末端断裂）

```
线索 → 主体+联系人 → 报价单 → 销售订单 → 采购订单 → 出货批次 → 【断】
                      ↑版本/成本快照      ↑以销定采        ↑分配行
```

| 环节 | 实现要点 | 证据 |
|---|---|---|
| 报价 → 订单 | 一次点击带出客户 / 术语 / 币种 / 汇率 / 明细；生成**草稿**；条件更新保证幂等 | `service/quotation.go:389-413` |
| 订单状态 | 10→20→30→40→50，未出货前可 90；跳步 409 | `service/sales_order.go:244-265` |
| 订单金额 | 入参 DTO 无合计字段，前端传了也在绑定阶段丢弃 | `dto/sales_order.go`、`service/sales_order.go:401-445` |
| 订单可改性 | 只有草稿可改可删，其余 409 | `service/sales_order.go:153,190` |
| 以销定采 | 明细挂 `sales_order_item_id`，三项校验 | `service/purchase_order.go:369-389` |
| 出货 | 分配挂订单行，未出量服务端算，排除已取消 | `service/shipment.go:274-319` |

#### 缺失点（按影响排序）

1. ~~出货之后没有钱~~ 已补一半（T-20）。应收应付能由订单生成，`RC` / `PY` 不再是空壳；
   但收款之后没有核销，`PM` 仍是空壳——「订单全流程」现在是「订单到开票」，还差「到收款」。
2. **出货不落到库存**。自持货场景下出货确认后库存不变，只能人工补出库单；而人工补的那张单
   与出货单没有引用关系，`单票毛利` 与 `库存对账` 都追不回去。
3. ~~信用额度是摆设~~ 已补（T-39）。字段有、界面能填、没人读，是「字段到位、消费方缺席」的
   典型样本。现在订单确认时按「未结清应收 + 已确认未开票订单」算敞口，超额 409；
   admin 可强制放行并落 warn 日志，T-33 落地后并入审计表。
4. **已确认订单没有合法改动路径**。现在只能 409 拒绝。现实的改价、改量、延迟交期会被逼成
   「删了重建」——单号变了，客户手里的那份对不上。
5. **没有履约视角**。订单列表看不到「已出多少 / 还剩多少 / 逾期未出」。这个数在仓储层已经算了
   （`ShippedQtyByOrder`，`repository/shipment.go:220`），只是没有暴露到列表与详情。
6. **订单没有审批**。大额订单、超折扣订单与普通订单走同一条路。

#### 改进建议

| 建议 | 任务卡 | 落点 |
|---|---|---|
| 出货确认生成销售出库单（同事务，带 `DN-` 单号引用） | T-40 | 出货 service 的状态流转 |
| 信用额度拦截（下单与确认两处，超额 409 + admin 强制放行留痕） | T-39 | `sales_order` service + T-33 审计 |
| 订单行履约数量暴露到列表（已出 / 未出 / 逾期） | 并入 T-28 销售看板 | 查询层聚合，不加派生列 |
| 已确认订单的变更单 | T-44 | 新表 + 状态机约束 |
| 报价与订单的改价审批（最小版） | 并入 T-33 | 审计表 + 一个 `requires_approval` 标记 |

### 4.2 客户与商机

#### 现状

- **主体是同一行数据**：客户与供应商是 `md_partner` 的两个角色位，`role` 为位掩码，
  列表筛选展开成 `IN` 而不是位运算（`repository/partner.go:144-149`）。这条设计是对的，
  货代就是照这个路子加的：`model/partner.go` 加一个常量、`roleNames` 补一行，
  查询与 handler 一行没改（T-17）。
- **商务条件已在主体上**：贸易术语、结算方式、账期、额度、默认币种。订单与报价各自再存一份
  贸易术语，主体上的那份是默认值。
- **联系人**：一个主体多行，有职位、语言、渠道；主联系人靠事务内先清后置。
- **跟进**：手工记录，`next_follow_at` 到期可筛。**不能挂商机**。
- **商机**：阶段可回退、终态不可改；赢单 / 输单概率强制 100 / 0；加权预测按阶段聚合。
- **线索**：转化时建主体并回填，重复转化 409。

#### 缺失点

1. **没有查重**。这是主流垂直软件的第一道防线 `[外贸垂直]`，也是本项目最便宜的改造：
   建主体前按「名称 + 国家」「邮箱域名」「电话」三组查一次，命中就给候选列表。
   代价低，收益是「客户 360 不会因为两条记录而失效」。
2. **转化线索时不查重**。线索转主体与手工建主体走两条不同的入口，查重只做一处等于没做。
3. **没有客户 360**。跟进、商机、订单、出货、应收分散在五个页面，回答「这家客户怎么样」
   要点五次。这不是报表需求，是唯一能兑现「CRM 与 ERP 共用一行数据」价值的界面。
4. **跟进不能挂商机**。现在只能挂主体，谈单细节只能写在主体跟进里，商机详情页空着。
5. **主体档案缺外贸字段**：税号（开票与报关用）、多地址（提单地址 ≠ 发票地址）、
   客户组 / 区域（报表分组用）。
6. **没有 ABC 分级与公海**。蓝图定的是 P2，同意；但要注意公海依赖「归属人」，
   而归属人要等 T-32 的 `owner_id`。所以公海只能排在 T-32 之后。

#### 改进建议

| 建议 | 任务卡 | 说明 |
|---|---|---|
| 客户查重与合并（三组规则 + 合并迁移引用） | T-41 | 合并必须留痕，依赖 T-33 |
| 跟进支持挂商机（`subject_type` + `subject_id` 或加 `opportunity_id`） | 并入 T-30 前置小步 | 建议加显式外键而非多态：只有两个对象，多态换来的是查不快 |
| 客户 360 | T-30（已有） | 聚合查询，不加派生列 |
| 主体补税号与多地址（新表 `md_partner_address`） | 并入 T-35 导入导出前置 | 地址是 1:N，不要往主表加 `address2` |

### 4.3 库存与采购

#### 现状

- **流水是事实、快照是缓存**：同事务写入，快照用 `ON CONFLICT ... qty = qty + ?` 原子加，
  另有全量重算作为对账手段。允许负库存（直发业务常态）。
- **确认才产生流水**：草稿改多少次都不动库存；确认后不可撤销，错了做反向单。
- **手工流水只放行期初 / 盘点盈亏 / 其它**，采购入库与销售出库必须挂单据。
- **采购价不从货源表取**（有意），汇率独立锁定，以销定采三项校验。
- **无仓库、无库位、无批次**；调拨类型编号已占但主动 400。

#### 缺失点

1. **出货与库存之间没有链路**（同 4.1）。这是当前库存最大的口径漏洞：货出了，账没动。
2. **单池模型撑不住「备货 + 直发」并存**。直发不需要库存，备货需要按仓看；现在两者共用一个
   产品维度的池子，备货的货与直发的货混在一起，「这个 SKU 还能卖多少」算不准。
3. **没有采购跟单节点**。外贸采购代理每天要回答的是「货在工厂还是已经进仓、验货过没过」，
   而系统里只有一张采购订单的状态。`[外贸垂直]` 的报价里「订单采备节点不清」是被明确点名的痛点。
4. **没有 ATP**。接单前判断能否按期发，现在靠人记；`shipment-candidates` 只回答「订单行还能出多少」，
   不回答「仓里够不够」。
5. **盘点差异没有原因分类**。差异直接生成流水，事后无法按原因（漏录、损耗、错发）统计。

#### 改进建议

| 建议 | 任务卡 | 说明 |
|---|---|---|
| 出货确认 → 销售出库（同事务、可配置「直发不落库存」） | T-40 | 与 4.1 同一条 |
| 仓库维度（快照唯一键改 `warehouse_id + product_id`） | T-16b（已有） | 触发条件见 7.3 |
| 采购跟单节点 | T-38 | 五节点 + 逾期视图 |
| 盘点差异原因枚举 | 并入 T-16 补丁 | 加一个字段，不改结构 |
| ATP | D5（蓝图已列） | 排在仓库维度之后才有意义 |

### 4.4 多币种结算

#### 现状

- **底座是对的**：唯一本币（`md_currency`）、汇率只追加、按生效日半开区间取、缺汇率直接 400
  而不是把 0 写进本币金额。`Convert` 是唯一折算函数。
- **完整四件套在 5 张主表落地**：报价单、销售订单、采购订单、商机、产品货源；
  报价明细额外存「原币金额 + 本币金额」两列，但不带币种与汇率（两者在主表），
  单币种单据下足够。
- **汇率在 service 写入时锁定**（`service/document.go:59-85`），符合跨模块约束。

#### 缺失点

1. ~~没有应收应付~~ 已补（T-20 + T-21 + T-23）：四件套两侧都有载体，应收锁销售汇率、
   应付锁采购汇率；核销时按到账汇率折本币，差额逐笔落成汇兑损益表
   （`/reports/exchange-gains`）。剩下的缺口是**期末重估**——未核销余额按期末汇率重新估值，
   本项目还没做，也不在 P1 主链上。
2. **单一汇率，没有买入 / 卖出价**。`[ERPNext-C]` 用 `For Buying` / `For Selling` 区分：
   银行卖美元给你的价与买你美元的价不同。本项目一张汇率表通吃，收汇与付汇用同一个数，
   单票毛利会系统性偏高或偏低（金额不大但方向固定，累计可观）。
3. **商机按当日汇率重算**（`service/opportunity.go:246`），预测随汇率漂。
4. **前端展示不考虑币种小数位**（`components/fields.tsx:20-29`）。后端 `Convert` 按目标币种
   小数位舍入，前端固定按 2 位显示——JPY 会显示成 `1,000.00`，而 KWD 的第三位被截掉。
   同时金额不带币种符号，混币种列表里无法辨认真假。
5. **金额是 `float64`**。外贸单据天然有「订金 30% + 尾款 70%」的分账，两笔相加必须等于总额，
   浮点在这个场景下迟早差一分。

#### 改进建议

| 建议 | 任务卡 | 说明 |
|---|---|---|
| 金额定点化（Decimal 类型 + 前后端字符串传输） | T-37 | 必须在 T-20 之前 |
| 汇率加 `rate_type`（买入 / 卖出 / 中间价），取价时按业务方向选 | 并入 T-20 前置 | 不加则先按中间价，写进口径注释 |
| 商机存「录入时本币金额」，预测用它；重算显式触发 | 并入 T-07 补丁 | 与「汇率随单据锁定」对齐 |
| 前端金额组件读币种小数位与符号 | 并入 T-37 | 与类型改造同批，改一处动全站 |

1. **成本与毛利对所有人可见**。这是蓝图 I 组开头点名的「最常见的泄密点」，也是这套系统
   在多人团队里能否推广的分水岭。
2. **没有归属人**。业务员看到全部客户，跟进责任无法在数据上体现；公海 / 私海、业绩归属、
   数据范围全都依赖它。
3. **没有审计**。「这张单的价格谁改的」答不出来，出了问题只能靠人回忆。
4. **角色写在令牌里**。降权不即时，且要即时失效必须删该用户全部会话（现在没有入口）。
5. **接口无资源级授权**。`GET /sales-orders/:id` 对任何登录用户返回完整单据，包括成本类字段。

#### 改进建议（三步，每步都可独立上线）

| 步骤 | 内容 | 侵入面 | 工作量 |
|---|---|---|---|
| 1 | 角色扩到 6 个 + 声明式路由授权（`secured.GET(path, role, handler)`，中间件比对） | `router.go` 全表 + 一张角色常量表 | 0.5～1 人日 |
| 2 | `owner_id`：业务表加列 + principal 带 `uid` + repository 统一注入 scope + 越权返回 403 / 不存在返回 404 | 23 张表、19 个 repository、20 个 service 的查询入口 | 2～3 人日 |
| 3 | 字段级脱敏：按角色在 DTO 投影阶段删字段（成本价、毛利率、采购价） | dto 层 + 前端按 `permissions` 隐藏列 | 1～2 人日 |

关键取舍两条：

- **`owner_id` 放 `Base` 还是只放业务表**：放 `Base` 一次到位，但 `sys_user`、`sys_doc_seq`、
  `md_currency` 这类不该有归属的表会被迫带上一个无意义的列。建议**只加在「有责任人的表」**上
  （主体、线索、商机、跟进、报价、订单、采购、出货、应收），主数据与系统表不加。
- **越权返回 403 还是 404**：项目已有先例（角色外 id 返回 404，`docs/architecture.md` 第四节第 9 条），
  理由是「不让状态码反推 id 归属」。数据范围沿用同一逻辑更一致——**别人的单据一律 404**，
  只有「同一个资源、角色不够」才 403（如业务员访问成本字段）。

## 五、架构评估

### 5.1 分层与依赖方向

**结论：方向正确，是这套代码最扎实的部分。** `handler → service → repository → model` 单向，
`service` 不碰 gin、`handler` 不碰 gorm，有 `go list` 自检命令可验证（`apps/backend/AGENTS.md:84-91`）。
泛型 `Base[T]` + `Scope` 把分页 / 计数 / 软删 / NotFound 收敛掉了，新增模块不用重写这套易错逻辑。

**与外贸场景不匹配之处**：分层是对的，但**缺一层「单据引擎」**。外贸系统的复杂性集中在单据上：
状态机、单号、金额汇总、明细增删、审批、留痕、打印。现在这些散在 4 个 service 里各写一遍
（见 1.3）。单据类型还会继续加（合同、应收、应付、收付款、报关单——至少 5 张），
每加一张就多一份复制。

**重构方向**：不做大重构，只抽两件：

1. `service/document.go` 扩成单据公共能力（状态机 + 单号已是公共的，再加「明细装配 + 合计校验」）。
2. `repository.Base.WithTx` 接入（见 5.1 的事务问题）。

**代价与风险**：抽公共装配函数要动 4 个 service 的 `buildItems`，每个都有测试覆盖
（`quotation_test` / `sales_order_test` / `purchase_order_test` / `stock_document_test`），
风险可控，约 1 人日。

**更严重的一处：跨仓储写操作没有事务。**

`WithTx` 存在但**全仓无调用点**（`repository/base.go:56`），事务全部由 repository 内部的
`db.Transaction` 自持，service 层拿不到事务句柄。后果是两处跨服务写操作只能靠补偿：

| 位置 | 现在的做法 | 失败后果 |
|---|---|---|
| `service/quotation.go:389-413` 转单 | 先建订单，再条件更新报价；更新失败就删掉刚建的订单 | 删订单也可能失败 → 留下没人认领的草稿单 |
| `service/lead.go:228-248` 线索转主体 | 先建主体，再标记线索；失败只记日志 | 留下孤儿主体（日志里有，列表里没有线索指向） |

现在能接受，是因为这两处的失败窗口极窄。**但应收应付落地后，「生成应收 + 回写订单」会变成
每天几百次的批量动作**，补偿式写法会开始漏。建议在 T-20 之前把 `TxManager` 做出来（T-42）。

### 5.2 模块划分（按层 vs 按域）

**结论：按层分包仍然正确，但按文档自己定的触发条件，切分点已经到了。**

`docs/architecture.md` 第四节第 8 条写明触发条件是「CRM 侧模块超过三个，或出现只属于一侧的
复杂逻辑」。现状：CRM 侧已有 `contact` / `activity` / `lead` / `opportunity` **四个**模块；
ERP 侧有 `quotation` / `sales_order` / `purchase_order` / `shipment` / `stock` / `stock_document`
六个 —— 条件按其自身标准已满足。

**但我的结论是「暂不按域拆目录」**，理由是拆的收益此刻低于成本：

- 目录拆分只解决「文件多」，不解决「改动同步」。报价、订单、出货的改动天然是同步的
  （加一个单据字段，四处都要动），按域拆反而把一次改动的 diff 摊到四个目录。
- 真正的痛点是 **service 之间的调用关系**：`quotation → sales_order`、`lead → partner`、
  `product_source → currency`。这个用目录治不了。
- 拆目录的代价是 19 个 model、20 个 repository、20 个 service、18 个 handler 的 import 路径全改，
  diff 巨大而行为零变化，评审时看不出来任何东西。

**替代方向（建议采纳）**：用**编译期约束**代替目录约束 —— 在 CI 里加两条 `go list` 断言：

```
service/erp 不得 import service/crm 的包   （方向：交易不反向依赖关系）
repository 不得 import service              （已有）
```

以及在 `bootstrap` 里显式声明依赖方向注释（现在已有一份装配顺序注释，`bootstrap/app.go:119-170`）。

**真正的切分触发条件**（写死在这里，避免以后又争论）：

1. 出现**跨域的报表查询**（如「按客户统计毛利」要 JOIN 订单、出货、应收、跟进四张表）——
   这时需要的不是拆目录，而是**独立的报表层**（`service/report`）与只读模型。
2. 团队超过 3 人并行改 ERP 与 CRM —— 目录冲突开始变成真实成本。
3. 某个域要独立部署（基本不会发生，见根 `AGENTS.md`「不做微服务」）。

### 5.3 数据模型

**结论：主数据与单据的骨架是对的（主表 / 明细 / 分配表 / 流水 / 快照五类齐备），
但有 3 处硬伤与 4 处结构缺口。**

硬伤：

| # | 问题 | 证据 | 后果 | 方向 |
|---|---|---|---|---|
| 1 | 金额与汇率全是 `float64` | 11 个 model 文件；`pkg/money` 只有一个 `Round` | 分账、核销、汇兑累计误差 | T-37 |
| 2 | 软删除 × 唯一索引互斥 | 除 `sys_doc_seq` 外所有 `uniqueIndex` 表都嵌 `DeletedAt`；`repository/stock.go:277-281` 的注释已承认快照这个坑 | 删掉一个产品后无法用同一个 SKU 重建；`service` 的前置查重看不到软删行，冲突走到 DB 变成 500 而不是 409 | T-45（已修：唯一索引改为 `(业务列, deleted_at)`，标记用整数，见 `docs/architecture.md` 第 7 节） |
| 3 | 派生数据与事实数据混放的风险点 | 目前守得住（无「最近跟进时间」列），但 `md_partner.contact` 已是冗余的主联系人姓名 | 一旦有人给它加同步逻辑，就会出现两个来源 | 维持现状，写进评审清单 |

结构缺口：

| 缺口 | 影响的能力 |
|---|---|
| 无 `owner_id` | 数据范围、公海、业绩归属、待办（I2 / B5 / I4） |
| 无仓库 / 批次 | 备货、调拨、追溯、ATP（T-16b / D5） |
| 无主体地址表（1:N）与税号 | 提单地址 ≠ 发票地址、开票与报关（G 组、E 组） |
| 无通用附件表 | 提单、报关单、验货报告扫描件（T-26） |

**一个可以不改的「重复」**：五张单据主表各自重复了 `partner_id / currency_code / exchange_rate /
amount_total / amount_base_total / trade_term / status / doc_no` 八个字段。看起来适合抽一个
`DocumentBase` embed（`Base` 已经证明 gorm embed 可行）。**但我建议不抽**：
gorm 的 embed 与软删、索引、`TableName` 的交互有坑（`apps/backend/AGENTS.md:391` 记录的
「改字段名没写 column 导致数据变空」就是同一类问题），而重复这 8 个字段的成本只是「加字段时多改几处」。
收益不抵风险。

### 5.4 接口设计

**做得好的**：统一响应体 `{code,message,data,request_id}`；错误码前三位对齐 HTTP 状态码；
分页三件套职责清晰；路由表只有一处；`/customers` 与 `/suppliers` 用同一个 handler 注入角色。

**问题清单**：

| 问题 | 证据 | 建议 |

| **查询参数白名单有两份实现**，前端那份会静默丢参数 | `providers/dataProvider.ts:30-46` 的 14 项白名单里没有 `from` / `to` / `sales_order_id`，而后端支持（`service/stock.go:85-94`、`service/shipment.go:161-164`） | T-43：白名单补齐并加一条「每个资源的筛选参数都有用例」的测试 |

## 六、权限与多租户

### 6.1 单租户方案（主推）

**目标口径**：单库、单租户、不做字段级权限矩阵；但**单租户内的数据范围必须做**（与根 `AGENTS.md`
第 1 节一致）。分三步，每步独立可上线、可回滚。

**第一步：角色 + 路由级授权**（T-32 拆分 A）

- 六个角色：admin / 主管 / 业务员 / 财务 / 单证 / 只读（蓝图 I1）。
  **先用常量而非角色表**：现在的角色是写死的两个值，改成表要连带做「角色管理界面」，
  而六个角色的语义本身还会变（没人能一开始就定准）。常量 + 一处 `roleAllowed()` 足够，
  等真的需要自定义角色时再建表，迁移成本是「一张表 + 一个查询」，不是全表改造。
- 声明式注册：`secured.GET("/sales-orders", roleSalesRead, h.List)`。中间件比对 principal 角色，
  不通过返回 403（10003）。**handler 不感知角色**——一旦 handler 里开始写 `if role == ...`，
  授权规则就有了 18 份副本。
- 顺带修一个现有缺陷：`RequireAdmin` 挂上去（至少挂用户管理与导入），否则它是死代码。

**第二步：`owner_id` 数据范围**（T-32 拆分 B）

- 只加在「有责任人的表」（见 4.5 的取舍），不加在 `Base`。
- 传播路径：`Principal.UID` → service 构造 `repository.Scope` → 每个 `List/Find` 注入。
  **注入点必须在 repository 的 filter 层**，不能在 handler 后置过滤（后置过滤意味着
  分页总数算错）。
- 规则：业务员见自己的；主管见本组（暂等同全部）；财务与单证见全部单据但不见客户跟进；
  只读见全部、无写权限。
- 越权语义：**别人的单据返回 404**（与现有 `/suppliers/:id` 口径一致），只有「同资源、角色不够」
  返回 403。

**第三步：字段级脱敏**（T-36）

- 在 DTO 投影阶段删字段，不在前端隐藏（蓝图 I6 已明确）。
- 第一批只脱敏三类：`cost_price` / `gross_profit` / `margin_rate`。
  脱敏清单写进 `docs/glossary.md`，避免每个模块各自决定哪个字段算「成本」。

**成本合计**：约 4～6 人日（含测试）。**顺序不能颠倒**：先做第三步、后做第二步是无效的——
没有归属人，脱敏只能按全局角色，业务员照样能看到全部客户的毛利。

### 6.2 若要做多租户：侵入点、成本与触发条件

**先给结论：现在不做，但要知道代价。** 现在的架构（单进程、无共享状态、存储可替换）
**已经可以用「一套代码 + 多份部署 + 各自独立库」满足多法人**——这通常就是真实需求，
而不是「一个库里装多个租户」。

如果真要做单库多租户（SaaS 化），侵入点如下：

| # | 侵入点 | 具体位置 | 漏改的后果 |
|---|---|---|---|
| 1 | 表结构 | 23 张表加 `tenant_id`；`Base` 加字段最省事，但会让 `sys_doc_seq` 这类表也带一个无意义列 | 漏一张表 = 跨租户读到别人的数据 |
| 2 | **唯一索引全部要改** | 9 处唯一键：`md_product.sku_code`、`md_partner.code`、`md_currency.code`、`md_exchange_rate(currency,base,date)`、`biz_quotation(doc_no,version)`、四张单据的 `doc_no`、`sys_user.username`、`sys_doc_seq(doc_type,period)` | 不加租户维度 → 两个租户不能有同一个 `PART-001`；加了但漏索引 → 建单 500 |
| 3 | 唯一本币 | `md_currency` 的「唯一本币」是全局约束（停用不删除） | 全库只能有一个租户设本币 |
| 4 | 发号器 | `sys_doc_seq` 的键要加租户，否则两个租户共用号段（单号会串，客户看到别人的单号） | 单号连续性失去意义 |
| 5 | 缓存 key | `session:{jti}`、`login_fail:{username}`、`dashboard:summary` 都不含租户 | `dashboard:summary` 直接串数据（现在就已经是全进程共享） |
| 6 | 令牌与会话 | JWT claims 加 `tid`；`Verify` 校验会话与租户一致 | 换租户不重新登录 |
| 7 | 迁移与种子 | `AutoMigrate` 无租户概念；`seed.go` 的演示数据要按租户建 | 新租户开箱即脏数据 |
| 8 | 测试 | `storage_test.go` 的三库断言全部要加租户维度 | 一致性保证失效 |
| 9 | 数据迁移 | 存量数据要指定「默认租户」并回填 | 老数据全部归属不明 |

**成本估算**：结构改造 + 查询注入 + 测试补齐约 **5～8 人日**；若已有生产数据，
迁移与回归另计 **3～5 人日**，且需要停机窗口。**风险最高的是第 2 项**：唯一索引漏改不会在
开发期暴露（数据量小、只有一个租户），只会在第二个租户入驻的那天集中爆发。

**触发条件**（满足任一条再做，否则用「多份部署」顶着）：

1. 同一套代码要同时服务多家互不相关的公司，且**不愿为每家单独部署**（真正的 SaaS 诉求）。
2. 集团内多法人，且**必须在一个界面上看合并报表**（这时需要的是 `company_id` + 合并层，
   而不是完整的多租户隔离——两者不是同一件事，别混）。
3. 客户的合规要求「数据必须物理隔离」，但又不接受独立部署（自相矛盾，通常说明该谈价格而非改架构）。

## 九、不建议做

与根 `AGENTS.md` 第 1 节、蓝图第六节的清单一致，这里只补**那两份没列、但很容易被顺手加上**的几条。

| 不做 | 原因 |
|---|---|
| 完整审批流引擎（可视化流程设计器） | 本项目真实的审批点只有三个（报价改价、订单变更、信用放行）。做引擎的成本高于做三个 `requires_approval` 标记；等第四个审批点出现再说 |
| 采购询价单（RFQ）与招标 | `[Odoo-P]` 有，但代理采购的询价发生在微信与邮件里，系统里再走一遍只会多录一次。跟单节点（T-38）才是真痛点 |
| 库存估值 / 到岸成本 / 总账 | 本项目没有会计科目体系，做估值没有账可对。单票毛利（T-22）用「收入 − 采购 − 运杂费」就够回答「这单赚没赚」 |
| BOM / MRP / 生产工单 | 代理采购不生产。`[外贸垂直]` 里生产模块属于制造型企业版本 |
| 单一窗口 / 船公司轨迹直连 | 蓝图第六节已列，维持不做 |
| 邮件 / WhatsApp 往来归档（IMAP 同步） | 要邮箱授权与合规评估，且绑定具体邮箱商；结论手工记一条跟进就够（蓝图 B2 的现状） |
| 现在就做多租户 | 见 6.2：真实需求通常是「多份部署」，成本差一个数量级 |
| 按域拆目录（`service/erp`、`service/crm`） | 见 5.2：改动天然同步，拆目录只增加 diff |
| 给单据表抽公共 `DocumentBase` embed | 见 5.3：gorm embed 与软删 / 索引的交互有已知坑，重复字段的成本更低 |
