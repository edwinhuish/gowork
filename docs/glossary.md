# 术语表

**职责**：业务对象叫什么、归哪个域、哪些说法不许用、命名规则——全项目的唯一事实来源。
**不管**：优先级（`docs/trade-erp-crm-blueprint.md`）、任务与进度（`docs/roadmap.md`）、
代码分层（`docs/architecture.md`）。其他文档提到业务对象时只引用本文的名字，不重复定义。
**相关**：`docs/architecture.md`（分层）、`apps/backend/AGENTS.md`（落地时的硬性规则）。

---

## 一、定位

GoWork 是外贸采购代理的 **ERP 与 CRM 集成系统**：一套主数据，两侧业务。
采购代理的日常是"替客户买、替客户发、盯住客户关系"，这三件事分别落在
ERP 的采购/出货链路、CRM 的客户关系链路上，共用同一份产品与往来单位数据。

**不是"两个系统对接"**——没有同步任务、没有第二份客户表。集成发生在数据层：
CRM 记的跟进对象与 ERP 开发票的对象是同一行 `md_partner` 记录。

而且**客户与供应商本身也是同一张表**。它们是同一个"往来单位"的两种角色，
用 role 位掩码区分，因此"既是客户又是供应商"的主体只有一条记录、一套联系方式。

## 二、三层域模型

```
        ┌──────────────── 共享主数据 md_ ─────────────────────┐
        │ 产品 Product · 往来单位 Partner（客户/供应商/两者） │
        └───────┬─────────────────────────────┬───────────────┘
                │                             │
    ┌───────────▼───────────┐     ┌───────────▼───────────┐
    │  ERP 域 biz_ / inv_   │     │  CRM 域 crm_          │
    │  采购 · 库存 · 出货    │     │  联系人 · 跟进 · 商机  │
    │  订单 · 对账           │     │                       │
    └───────────────────────┘     └───────────────────────┘
```

| 域 | 管什么 | 表前缀 | 引用的主数据 | 当前状态 |
|---|---|---|---|---|
| 共享主数据 | 被两侧反复引用的实体 | `md_` | — | 已实现 |
| ERP | 交易与供应链：报价、订单、采购、出货、库存 | `biz_`（单据）`inv_`（库存） | 产品、往来单位（供应商角色） | 主链已实现；对账（应收应付）未做 |
| CRM | 客户关系：联系人、跟进、商机、线索 | `crm_` | 往来单位（客户角色）、产品 | 已实现 |
| 系统 | 账号、角色、单号号段 | `sys_` | — | 已实现（角色只有字段，无授权） |

**为什么往来单位不放进 `crm_`**：客户是 ERP 开发票、CRM 做跟进的同一个主体。
把它归给任何一侧，另一侧就得跨域引用，域边界立刻失效。判断标准是
"这张表会不会被两个域同时写"——会，就留在 `md_`。

**为什么客户与供应商不拆成两张表**：拆开的代价在"同一主体既是客户又是供应商"时
立刻显现——两行数据、两套联系方式、两个编码，对账时还要人工确认它们是同一家公司。
合并后一笔业务引用同一个 id，往来余额可以直接按主体归集。

## 三、术语表

"主要使用方"表示哪一侧以它为主；标记两侧的即为共享数据。

### 主数据

本表未标注状态的都已经实现；未实现的在条目里注明。

| 中文 | 英文标识 | 定义 | 主要使用方 |
|---|---|---|---|
| 产品 | `Product` | 可售卖的最小实体，以 SKU 编码唯一标识。价格、规格、包装是它的属性，不是它的身份 | ERP + CRM |
| 产品编号 | `ProductCode` | `md_product_code` | SKU 之外的**别名**：旧 SKU、客户物料号、工厂号，以及供应商给过但**没挂在货源上**的货号。`code` 原样保存用于显示，`code_norm` 是检索用的归一化形态（转大写、去空格与 `-_./`）。只服务搜索，**不上单据、不进打印件**；同一产品内 `code_norm` 唯一，跨产品可共用（两家客户从同一工厂拿货，工厂号相同是常态）。改 SKU 时旧码自动沉淀为 `source=sku`；`source` 取 `sku` / `customer` / `supplier` / `factory` / `other`。挂在某条货源上的供应商货号**不复制进来**——它跟着供应商与采购价走，真相在 `md_product_source.supplier_sku`（另存 `supplier_sku_norm` 参与同一次检索） | ERP |
| SKU 编码 | `SKUCode` | 产品唯一编码，格式 `类别(2) + 子类(2) - 流水(4)`，如 `BH01-0023`。全库唯一、永不复用；**改码时旧值自动沉淀为一条 `ProductCode`**，历史码仍能被搜到。新建的 SKU 也不得等于任何产品已存在的 `code_norm`，否则改出去的旧码会被新码占用，"永不复用"只守住了一半 | ERP + CRM |
| 产品类别 | `Category` | 两字母类别码（`HT` / `PT` / `BH` …），与 SKU 编码前两位一致 | ERP + CRM |
| 报关要素 | `HSCode` / `DeclaredNameCN` / `DeclaredNameEN` / `Material` / `OriginCountry` / `LegalUnit` | 产品的**默认**报关要素，六项全部选填：HS 编码、申报品名（中英）、材质与用途、原产地、法定单位。它们只是带出来的缺省值——HS 编码随目的国与用途变，真实申报以出货批次上填的为准。`LegalUnit` 与业务单位 `Unit` 是两个量纲（报价按箱、报关按千克），不可互相复用 | ERP |
| 往来单位 | `Partner` | 客户、供应商与货代的统一主体。一个主体可同时承担多种角色，此时只有一条记录、一套联系方式 | ERP + CRM |
| 主体编码 | `Partner.Code`（列名 `code`） | 主体的业务编码，也是案号的前缀（`DZ` → `DZ2603-QT01`）。**不得以数字结尾**：案号靠「编码 + 2 位年 + 2 位序号」分段，尾部是数字就分不清哪几位是编码 | ERP + CRM |
| 主体角色 | `PartnerRole` | 位掩码：`1` 客户 / `2` 供应商 / `4` 货代；叠加时按位相加（`3` 客供两用、`5` 客户兼货代） | ERP + CRM |
| 主体类型 | `PartnerEntityType` | `0` 公司 / `1` 个人。个人主体的报关资料与发票抬头和公司不同 | ERP + CRM |
| 供应商角色 | `PartnerRoleSupplier` | 角色位 `2`。代码里说"供应商"指的是**这个角色**，不是一张表 | ERP |
| 客户角色 | `PartnerRoleCustomer` | 角色位 `1`。同上 | ERP + CRM |
| 货代角色 | `PartnerRoleForwarder` | 角色位 `4`。替我方向承运人订舱、报关的主体，报关行也用这一位。它不参与采购与报价，所以主体上的贸易术语、账期、信用额度对它没有意义；对外入口是 `/forwarders` | ERP |
| 主体查重 | `PartnerDuplicate*` | 判断"这条会不会就是已有的某一家"。三条规则，命中任意一条即算像：**名称+国家**（转小写、去掉字母数字以外的字符，**不剥公司后缀**）、**邮箱同域**（免费邮箱名单整体排除）、**电话数字尾 9 位**。归一化在 `model/partner_dedupe.go` 里现算、**不落库**，规则改了不用回填全表。**只提示不阻断**：同名公司跨国家确实存在，拦住等于让人把询盘丢掉 |
| 主记录 | `Survivor` | 合并时**留下**的那条主体：保留自己的编码、名称与所有非空字段，角色取并集。账期与额度不从被合并方补位——`0` 有业务含义（款到发货 / 不限），填进去等于收紧结算条件 |
| 被合并方 | `Source` / `Absorbed` | 合并时被并走的那条：全部引用迁到主记录后**软删**。软删而非硬删，因为"这是一家"是人的判断，判断错了还要能把引用搬回去 |
| 主体合并 | `Merge` | 把两条往来单位并为一条。引用按 `repository/partnerRefTables`（15 张表 + 附件）在一个事务里整体迁移；主记录已有主联系人时把被合并方的降级为普通联系人；货源同产品同货号冲突时**拒绝**（409）而不是自动丢掉一条 |
| 联系人姓名 | `Partner.ContactName` | 主体上的**单个**主联系人姓名（列名 `contact`）。完整联系人（多个、各有电话邮箱）是 CRM 的 `Contact` 实体，一行一个自然人 | ERP + CRM |
| 系统账号 | `User` | 登录系统的操作者，与往来单位的联系人无关 | 系统 |

### 底座（已实现）

这几张表本身不是业务单据，但被每张单据引用，所以口径必须统一——它们是全系统的公共分母。

| 中文 | 英文标识 | 表名 | 定义 | 主要使用方 |
|---|---|---|---|---|
| 币种 | `Currency` | `md_currency` | ISO 4217 三位代码（`USD` / `EUR` / `CNY`）+ 小数位。全库有且只有一个本币 | ERP + CRM |
| 本币 | `BaseCurrency` | — | 记账本位币，`Currency` 里 `is_base` 的那一条。不是配置项：它出现在每张单据的本币金额里，必须可查 | ERP |
| 汇率 | `ExchangeRate` | `md_exchange_rate` | 某币种在某生效日相对本币的折算率，`1 外币 = rate 本币`。按日追加历史，不覆盖 | ERP + CRM |
| 单据编号 | `DocNo` | 列名 `doc_no`（`uniqueIndex`） | 单据的唯一编号，两种形态：报价与销售订单是 `{案号}-{类型}{NN}`（`DZ2603-QT01` / `DZ2603-SO01`），采购与送货单是 `{类型}-{YYMM}-{NNN}`（`PO-2610-001` / `DN-2610-001`）。全局唯一、永不回收；同一票的送货单 / 商业发票 / 装箱单共用送货单这一个号（即套号）。与主键 `id` 是两回事；同一份报价的多个版本共用同一个 `DocNo` | ERP |
| 案号 | `BaseNo` | 单据表上的 `base_no` 列 | `{客户编码}{YY}{NN}`，如 `DZ2603`，读作「DZ 客户 2026 年第 3 笔生意」。**不唯一**（报价与它转出的订单共用），只覆盖报价与销售订单；采购与送货单不挂它 | ERP |
| 套号 | `ShipmentSetNo` | 派生值，等于送货单的 `doc_no`，不单独落库 | 一票货的三份文件共用的号：送货单 / 商业发票 / 装箱单内部都印它，只有文件名加 `-DN` / `-CI` / `-PL` 区分。改证重开升版本 `DN-2610-001-R1`，不换号；不同票不得同号 | ERP |
| 号段 | `DocSeq` | `sys_doc_seq` | 号段 → 已发出的最大序号。案号的键是 `deal:{partner_id}:{yy}`；采购与送货单的键是 `(doc_type, period)`，`period` **存 `YYYYMM`、单号里只展示 `YYMM`**（存 4 位年，2100 年才不会与 2026 年撞到同一行）。不嵌 `Base`：号段若可软删除，号码就能重发 | ERP |

| 中文 | 英文标识 | 表名 | 定义 |
|---|---|---|---|
| 产品货源 | `ProductSource` | `md_product_source` | 某产品在某供应商处的采购来源与货号、价格、交期。一个产品可有多个货源 |
| 报价单 | `Quotation` | `biz_quotation`（明细 `biz_quotation_item`） | 向客户发出的价格方案，含贸易术语、币种、有效期与多轮版本 |

| 订单变更单 | `SalesOrderChange` | `biz_sales_order_change`（明细 `biz_sales_order_change_line`） | 已确认订单的改量 / 改价 / 改交期记录：原因、操作人、每行的前后值。**订单本身更新到新值**，变更单只留痕。单号由订单号派生（`{订单号}-CH{n}`），不单独发号。**不允许增删行**——出货分配与以销定采都按明细行 id 引用 |
| 采购订单 | `PurchaseOrder` | `biz_purchase_order`（明细 `biz_purchase_order_item`） | 向供应商下达的订单，可挂到销售订单行上 |
| 出货批次 | `Shipment` | `biz_shipment`（分配 `biz_shipment_allocation`） | 一次实际发运。与订单是多对多（分批出货、合并出货） |
| 库存流水 | `StockMovement` | `inv_stock_movement` | 每一次出入库记录，库存的权威来源 |
| 出入库单 | `StockDocument` | `inv_stock_document`（明细 `inv_stock_document_item`） | 采购入库 / 销售出库 / 盘点三类共用一张表，用 `type` 区分；**确认才产生流水** |
| 库存快照 | `StockSnapshot` | `inv_stock_snapshot` | 当前库存，只能由流水重算，用于对账与性能 |
| 运费杂费 | `ShipmentCharge` | `biz_shipment_charge` | 归集到出货批次的海运费、报关费、拖车费、保险费。金额按「原币 + 币种 + 本币 + 汇率」四件套存；**只登记我方承担的费用**（FOB 下客户付的运费不录），是单票毛利的减项 |
| 报关单 | `CustomsDeclaration` | `biz_customs_declaration` | 一票货的海关申报记录，含报关单号、申报日期、监管方式与退单状态。**一票可多张**：不同 HS 编码分票申报、被退单改单重报都是新的一条，旧单留着。报关单号是外部号，只记录、不参与发号与唯一性 |
| 物流节点 | `Shipment.BLNo` / `Vessel` / `ETD` / `ETA` | `biz_shipment` 的四列 | 提单号、船名航次、预计开船、预计到港。它们**订舱之后才有**，所以走独立入口（`PUT /shipments/:id/logistics`）、任何状态都能改，不受"出货单只有草稿能编辑"的限制 |
| 装箱数据 | `ShipmentAllocation.Cartons` / `GrossWeight` / `NetWeight` / `Measurement` | `biz_shipment_allocation` 的四列 | 这一行货物的箱数、毛重、净重与外箱尺寸，印装箱单（PL）用。挂在**分配行**而不是票头：一票装多种货时，票头那个总数拆不回任何一行，客户就无法逐行核对。重量是**整行合计**而不是单箱——改箱数才不用把所有合计重算一遍。0 与空串表示「还没装箱」，打印件上印「—」而不是 0 |
| 箱唛 | `CartonLabel` | 不落库，`GET /shipments/:id/carton-labels` 现算 | 贴在纸箱上的唛（shipping mark），一箱一张，文件名 `{套号}-MARK.pdf`。系统只印两样：销售订单号（主标识，最大字号）与套号当发票号；箱号、毛净重、尺寸留白给人工填，系统不出箱明细、也不承诺箱号连续。混装箱（一箱装多张订单的货）不生成，人工排版 |
| 应收单 | `Receivable` | `biz_receivable` | 应向客户收取的一笔款项。由销售订单生成，币种与汇率**从订单锁定**。**一期一张单**：同一订单的 30% 订金 / 70% 尾款是多张单，各自带到期日与号——核销按单进行，分期在单内就得再指定"核销第几期" |
| 应付单 | `Payable` | `biz_payable` | 应向供应商支付的一笔款项。规则同应收，来源只有采购订单。采购币种常与销售不同（收美元付人民币），所以汇率单独锁一份，不拿销售的汇率去折 |

|---|---|---|---|
| 启用状态 | `EnableStatus` | `1` 启用 / `0` 停用 | 这条**主数据或账号**还能不能被业务引用。停用不删除，历史单据仍指得到 |
| 单据状态 | `DocumentStatus` | `10` 草稿 / `20` 已确认 / `30` 备货中 / `40` 已出货 / `50` 已完成 / `90` 已取消 | **业务单据**的流转阶段 |

两者是不同类型，不要共用字段、不要共用一个 `status` 列。

`DocumentStatus` 的取值**故意留空档**（10 / 20 / 30 …）：将来要在"已确认"和"备货中"之间
插一个"已收订金"，只需给一个新值，不用把已有记录的 30 改成 40。连续编号看着整齐，
但它的整齐是拿历史数据换的。


### 角色的位掩码（合并客户与供应商的产物）

角色用位掩码而不是 `1=客户 / 2=供应商 / 3=两者` 的连续枚举。理由是角色天然是集合。
这一点在加第三种角色（货代）时兑现了：位掩码只是多一个 `4` 常量、在 `roleNames` 补一行，
查询侧 `RoleValuesContaining` 自动把「包含该位」展开成 `IN` 集合；若当初用连续枚举，
这一位要插成 `7`，把 `3` 挤走，所有 `role == 2` 之类的判断都得回头改一遍。

代价是**判断必须按位**：

```go
role.Has(model.PartnerRoleSupplier)  // 对
role == model.PartnerRoleSupplier    // 错：值为 3 的主体被判成"不是供应商"
role&model.PartnerRoleSupplier != 0  // 对，Has 内部就是这么写的
```

```ts
(role & PARTNER_ROLE.supplier) !== 0  // 对
role === 1                            // 错，理由同上
```

还有一处只有位掩码才会遇到的细节：按角色**筛选列表**时不能用
`WHERE role = ?`，那样会把"客供两用"的主体漏掉。查询要展开成
`role IN (...)`（Go 侧是 `model.RoleValuesContaining`），既覆盖全部组合，
又能命中 role 上的普通索引——直接写位运算条件在 PostgreSQL 和 MySQL 上都走不了 btree。

## 四、易混词对照

左列是**本项目不允许出现**的说法，右列才是对的。

| 不要用 | 用 | 原因 |
|---|---|---|
| Active / 在售 / 有效 | Enabled / 启用 | 同一个 `status=1` 曾有三种叫法，代码、文档、界面各说各的 |
| Contact（指人名时） | `ContactName` | `Contact` 是 CRM 实体，不是字段 |
| `code`（指 SKU 时） | `sku_code` / `SKUCode` | 往来单位也有 `code`，语义不同 |
| Status（脱离上下文的裸写法） | `EnableStatus` / `DocumentStatus` | 不带限定词的 status 无法判断是哪套状态 |
| vendor | Supplier（角色名） | 角色仍叫 supplier，承载它的实体叫 partner |
| client | Customer（角色名） | 角色仍叫 customer，承载它的实体叫 partner |
| 客户表 / 供应商表 | `md_partner` + 角色过滤 | 合并后只有一张表；`/customers`、`/suppliers` 是同一资源按角色切的入口 |
| 客供两用 / 双向往来（作为角色取值） | `role = 3`（客户\|供应商） | 它是两个角色位的组合，不是第三个角色 |
| 个人客户 / 公司客户（作为两个类型） | `PartnerEntityType` | 主体类型与角色是两个正交维度，别混成一个字段 |
| 商品 / 货品 | 产品 | `Product` |
| 货号（指我方身份） | SKU 编码 `SKUCode` | 货号是供应商侧与客户侧各自的叫法，都不是我方身份；我方身份只叫 SKU 编码 |
| 把客户物料号 / 旧 SKU 写进 SKU 或备注 | 记成一条 `ProductCode`（`source=customer` / `sku`） | SKU 是身份，全库唯一且永不复用；塞进去之后客户换号或我方改号都得改 SKU，历史单据与旧报价当场对不上 |
| 货代 / 承运人 / 报关行（混着叫） | 往来单位的货代角色 `PartnerRoleForwarder`（位 `4`） | 三者都在替我方跑单证，但系统只登记**与我方有委托关系**的那个主体。承运人（船公司、航空公司）是货代的下游，它的提单号、`DO` 是外部号，记在单据上而不是建一个主体；报关行与货代共用这一位，因为同一家常同时做两件事 |
| HS 编码只存在产品上 | 产品上的只是默认值，真实申报以出货批次为准 | 同一产品出口欧盟与美国可能归不同税号；把产品上的编码当唯一事实，改一票货就要改主数据，已经出过的单也跟着变了 |
| 型号（当成产品身份） | `ProductCode`（产品编号） | 客户与工厂嘴里的「型号」就是一条编号，落 `md_product_code` 当检索别名；它不是 SKU 编码，也不是规格 `Spec` |
| 把 `ProductCode` 当 SKU 用 | `SKUCode` | 编号只服务搜索；列表与单据的主字段只认 SKU 编码，命中编号只在搜索时作为辅助行出现 |
| 把编号印进单据 / 打印件 | 单据只印 `SKUCode` | 同一张单出现两套叫法，对账时必然有人按另一套找 |
| 编号（裸写） | 产品编号 `ProductCode` / 单据编号 `DocNo` / 案号 `BaseNo` | 三者互不相干：产品编号回答"这个词能不能找到产品"，单据编号是单据对外的唯一标识，案号只回答"属于哪笔生意" |
| 供应商货号（简写「货号」） | `supplier_sku`（`ProductSource.SupplierSKU`） | 与 SKU 编码不是一回事：前者是对方目录里的叫法，后者是我方的身份 |
| `lead_time` / 货期（作为字段名） | `delivery_days`（交期天数） | 本库里 `Lead` 已经是 CRM 的线索，`lead_time` 在搜索与讨论里会被读成「线索时间」 |
| 单据（泛指任何记录） | 明确说是主数据还是单据 | 单据特指有状态流转的业务凭证 |
| 订单（裸写） | `SalesOrder` / `PurchaseOrder` | 两个方向都有订单，裸写「订单」时无法判断谁向谁下 |
| 发货 / 出运 / 发货单 | 出货批次 `Shipment` | 三个叫法指同一件事；「出运」只在报关语境里用 |
| 运费 / 杂费 / 货代账单（混着叫） | 运费杂费 `ShipmentCharge` | 一批钱按行登记、按类型分（海运费 / 报关费 / 拖车费 / 保险费 / 其它）。账单是凭证不是实体：系统不建「账单表」，一张账单拆成几行、或几张账单合成一行都可以 |
| 报关费 / 关税（混着叫） | 报关费是 `ShipmentCharge(type=20)`；关税不进系统 | 报关费是我方付给报关行的服务费，进我方成本；关税与进口增值税由进口方在目的国缴纳，我方出口一般不承担 |
| 报关单号 / 提单号 / 内部单号（混着叫） | 前两个是**外部号**，只有出货单号（`SH-`）是自己发的 | 报关单号由海关给、提单号由承运人给。它们只记录、不参与发号与唯一性：让系统再编一个号，对单时就要多一层翻译。回查靠 `shipment_id`，不靠号 |
| 退单 / 作废（混着叫） | 报关单「已退单」（`CustomsStatus=90`） | 退单是海关退回要求修改，改完还要重新申报，单据仍然有效；作废是另一回事，且通关过程中不存在"作废这张报关单"这个动作 |
| ETD / ETA / 出货日（混着叫） | `ETD` 预计开船、`ETA` 预计到港、`ShipDate` 出货日 | 出货日是我方发货那天（决定它落在哪个统计月份、只能草稿改）；ETD/ETA 是船期（订舱后才有、任何状态都能改）。三者经常不是同一天 |
| 把客户承担的费用也录进来 | 只录我方承担的费用 | FOB 下海运费客户付。录进来会被算成我方成本，毛利凭空低一截而钱一分没花；客户承担又由我方垫付的情况，要等 T-20 的应收载体才冲得掉 |
| 已出数量（不说明含不含已取消的票） | 有效出货已占数量（`Shipment.Status <> 已取消`） | 把取消的票也算进去，可用量会凭空少一截，而货一件都没出 |
| 剩余数量 / 还有多少（指出货口径时） | 未出数量 = 订单行数量 − 已占数量 | 它和库存不是一回事：这张订单还没出的量，可能连货都还没采购 |
| 报价 / 价格表 / 报价方案 | 报价单 `Quotation` | 价格表是产品属性，报价单是有有效期与版本的凭证 |
| 询价单（指系统里的 `Quotation`） | 报价单 `Quotation`（类型码 `QT`） | 实体是报价单；`QT` 只是单号里的类型码，"询价"是它的业务前身，不是第二张表 |
| 单号 / 订单号（泛指） | 对外用 `DocNo`；提到「哪笔生意」时用案号 `BaseNo` | 两者不是一回事：`DZ2603-QT01` 与 `DZ2603-SO01` 是两张单（各有各的 `DocNo`），共享同一个案号 `DZ2603`；而 `DN-2610-001` 是另一票货的单号，与案号无关 |
| 主单号（当作对外单号用） | 案号 `BaseNo` | 它不唯一，也印不到报关与收汇资料上：客户问"单号"时给的是 `DocNo` |
| 送货单号 / 出货单号 | 出货批次的 `DocNo`（`DN-2610-001`） | 实体是 `Shipment`，`DN` 只是它的单号；`DN`（我方送货单）≠ `DO`（货代或船公司的提货单），后者是外部号 |
| 发票号 = 订单号 | 商业发票与送货单同号（套号 `DN-2610-001`），与订单号无关 | 报关与收汇认的是发票号；拿订单号当发票号，改证重开时无号可发 |
| 一套单证各发各的号 | 同一票的 DN / CI / PL 共用套号（`DN-2610-001`） | 三个文件内部编号一致，客户与报关不用做映射；不同票不得同号，改证用 `-R1` |
| 箱唛印送货单号 | 箱唛主标识印销售订单号（`DZ2603-SO01`），送货单号作辅助栏位 | 客户按订单分货；改证重开只让发票版本变，订单号永久有效，所以订单号做主标识、发票号做成贴纸随版本换 |
| 合并出货把号挂在某一张订单下 | 送货单独立发号 `DN-{YYMM}-{NNN}` | 一票属于多笔生意，号挂任何一家都失真；"装了哪几张单的什么"由分配行回答 |
| 把箱数毛净重记在票头上 | 记在分配行（每行各自的箱数、毛净重与尺寸） | 一票装多种货时票头只有一个总数，装箱单逐行核对时拆不开；合计由明细相加得出，另存一份迟早对不上 |
| 改单 / 修正（对已确认的报价） | 另存新版本（`version` 递增） | 已确认的报价单是发给客户的承诺，改它等于改历史；同一份报价共用 `DocNo` |
| 成本价（不说明口径） | 货源本币价 / 报价单明细上的成本快照 | 前者是会变的主数据，后者是写下单据那一刻的锁定值 |
| 汇率 / 汇价 / 兑换率 | `ExchangeRate` | 三处各写一个名字，最后会有人以为它们是三个概念 |
| 币种 / 货币 / 结算币 | `Currency` | 用「币种」；「结算币」是单据上的字段语义，不是实体 |
| 金额（不说明计价口径） | 原币金额 / 本币金额 | 跨币种单据上两者相差一个汇率，裸写「金额」必然被误读 |
| 客户（指线索时） | `Lead` | 线索还没建档，没有 `md_partner` 记录，不算客户 |
| 联系人（指主体上的主联系人） | `ContactName` | 同第 122 行的规则，只是这次要区分「多人中的主联系人」 |
| 库存（指快照） | `StockSnapshot` | 「库存」既可指流水也可能指快照，查询与修正走的是两套规则 |
| 调数 / 直接改库存 / 盘一下 | 补一条库存流水（`inv_stock_movement`） | 快照只能由流水推出来；直接改快照之后，快照与流水谁对谁错再也判断不了 |
| 数量（带方向 vs 带符号） | 流水：`qty` 正数 + `direction`（±1）；聚合：`SUM(direction * qty)` | 把出库记成负数会让"两条 +5"与"一条 −10"同样合法，对账时无从判断 |
| 核销 / 冲销 | 核销 `PaymentAllocation`（`biz_payment_allocation`） | 「冲销」是财务的红字冲回，与把收款对应到应收不是一回事 |
| Party / party | `Partner` / `partner` | Party 在合同语境里指「当事方」，日常又容易被读成「聚会」，做主数据实体名两头都不贴切；Partner 才是「业务伙伴」的行业说法。表名同理：`md_party` → `md_partner` |

## 五、命名规则

### Go

| 规则 | 例子 |
|---|---|
| 缩写词全大写（Go 官方 Code Review Comments） | `SKUCode`、`UserID`、`TokenID`、`HTTP`、`DSN`、`CORSOrigins`、`JWT`。不写 `SkuCode`、`UserId` |
| 导出标识符 PascalCase，包内 camelCase | `ProductService`、`normEnableStatus`、`enableStatusPtr` |
| 接口以职责命名，不加 `I` 前缀 | `ProductRepository`，不是 `IProductRepository` |
| 构造函数 `New + 类型名`，可选依赖走 Option | `NewProductService(repo, WithProductLogger(log))` |
| 仓储查重方法带列语义 | `ExistsBySKUCode` / `ExistsByCode`，不写含糊的 `Exists` |
| 布尔方法用 `Is` / `Has` / `Can` 开头 | `IsEnabled`、`IsAdmin` |

### TypeScript

| 规则 | 例子 |
|---|---|
| 组件 PascalCase，文件名与导出一致 | `ProductList`、`form-fields.tsx` 导出多个字段组件 |
| hook 以 `use` 开头 | `useTable`（refine 提供）、`useForm` |
| 常量 UPPER_SNAKE_CASE | `ENABLE_STATUS_OPTIONS`、`PAGE_SIZE` |
| 类型/接口 PascalCase，不加 `I` 前缀 | `Partner`、`PageResult<T>` |
| 字段名与后端 JSON 完全一致（snake_case） | `sku_code`、`created_at`，不要在这里转 camelCase |

### 数据库与 API

| 对象 | 规则 | 例子 |
|---|---|---|
| 表名 | `前缀_单数_snake` | `md_partner`、`sys_user`、`biz_sales_order` |
| 列名 | snake_case，与 JSON tag 对齐 | `sku_code`、`supplier_id`、`entity_type` |
| 主键 | 一律 `id`，自增 `uint` | 见 `docs/architecture.md` 第五节 |
| API 路径 | 复数、kebab-case | `/api/v1/products`、`/api/v1/partners`、`/api/v1/sales-orders` |
| JSON 字段 | snake_case | `product_total`、`enabled_products` |
| 单据编号列 | 一律 `doc_no`，加 `uniqueIndex` | `biz_sales_order.doc_no` = `DZ2603-SO01` |
| 币种列 | `currency_code`，存 ISO 4217 三位代码 | 不要存币种 `id`：单据要能脱离主数据读懂 |
| 金额列 | 跨币种单据必须成对出现 | `amount`（原币）+ `amount_base`（本币），另存 `exchange_rate` |
| 单据状态列 | 一律叫 `status`，类型 `model.DocumentStatus` | 与主数据的 `status`（`EnableStatus`）同名不同型，靠类型而非列名区分 |

**列名与 Go 字段可以不同，但必须有理由。** 例：`Partner.ContactName` 的列名是
`contact`，因为改名会让 AutoMigrate 新增列、把既有数据留在旧列里。
这类偏离要在结构体上写明原因，不能只靠 commit message。
